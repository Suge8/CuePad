# CuePad 开发文档

CuePad 是 Swift 原生应用：macOS 26+、iOS/iPadOS 27+，iCloud 同步，Pi 深度集成。Swift 6 严格并发，界面 SwiftUI，编辑器与菜单栏面板用 AppKit/UIKit。产品定位与功能见 [README.md](../README.md)；模块索引见 [AGENTS.md](../AGENTS.md)。

## 环境与命令

需要 Xcode 27。统一入口 `apple/scripts/xc.sh <build|test|shot> <mac|ios|ipad> [截图路径]`（`ios` 是 iPhone 模拟器，默认 `iPhone 17`，`CUEPAD_IOS_DEVICE` 覆盖；`ipad` 是 iPad 模拟器，`CUEPAD_IPAD_DEVICE` 覆盖），退出码即 xcodebuild 的退出码。共用 Swift 包在 `apple/CuePadKit`，直接用 SwiftPM。

```bash
apple/scripts/xc.sh build mac
apple/scripts/xc.sh test mac
apple/scripts/xc.sh build ios
apple/scripts/xc.sh test ios        # 同一测试目标，跑其中 iOS 也编译的部分（Swift Testing；摘要里的 "Executed 0 tests" 只数 XCTest）
apple/scripts/xc.sh shot mac        # 构建 → 后台启动 → 单窗口截图 → 退出，输出 .derived/shot-mac.png
cd apple/CuePadKit && swift test    # 共用包的全部测试
cd apple/CuePadKit && swift build -c release --product cuepad   # 命令行
```

构建产物在 `apple/.derived/`（自带 `.gitignore`）。**并行的 agent 必须各用一个产物目录**（`CUEPAD_DERIVED=/tmp/xxx apple/scripts/xc.sh …`，截图、隔离库、Pi 目录随之落在该目录下），共用同一个目录时构建与测试会互相覆盖而随机失败。

## 代码地图

`apple/CuePad.xcodeproj` 是一个多平台 App target（macOS + iOS/iPadOS）加分享扩展、小组件与命令行三个目标；源码在 `apple/App/Sources/` 与 `apple/App/Tests/`（文件夹同步组，增删文件不用改工程文件）：

| `App/Sources/macOS/` | 壳层：窗口、全局快捷键、菜单栏图标与面板 |

| `App/Sources/UI/` | 界面：`Shared/`（组件、主题、规则、工作区状态）、`macOS/`、`iOS/`、`Debug/`（视觉验收场景与演示数据） |
| `App/AppGroup/`、`ShareExtension/`、`Widget/` | iOS 的 App Group 位置与快照、分享扩展、小组件 |

| `scripts/` | `xc.sh` 与签名、发布脚本 |

## 产品模型

功能只服务一条循环：**捕获 → 打磨 → 发出 → 回看**。

| 概念 | 定义 |
| --- | --- |
| 项目 | 灵感与任务的容器，带一句可选的介绍（`intro`），没有目标卡；可绑定一个文件夹（每台 Mac 各自绑；Mac 上用系统的选文件夹面板，手机经投送请求让那台 Mac 绑，新建项目时也可选），Pi 会话与 `cuepad` 命令行按工作目录自动归入，新会话也开在这个文件夹里 |
| 灵感 | 唯一的内容类型：文字 + 内联图片 + `{{变量}}` + 分割线。思考、笔记、提示词都是灵感；挂在任务下的灵感在任务里叫提示词 |
| 任务 | 要做的灵感：与灵感是同一种记录（`Card`），"设为任务 / 改回灵感"在两者间切换；可放在项目里或未分类；任务是一件要做成的事，正文只有标题与一句说明（`CueTask`，存两行；多行的话设为任务、新建任务时第一行留给任务，其余成为它的第一条提示词，`CueStore.splitPrompt`）；挂在任务下的灵感是提示词（要交给 Agent 的话）、挂在任务下的任务是子任务，只有任务能当上级，最多三级；提示词交给 Agent 后，没有请求还在路上、且最近一次发给 Pi 会话之后那个会话歇下（`stateSince` 晚于发出）或对话里有之后的一条回答，就算"已回复"；没回答就结束的不算；由发送记录、投送请求、会话状态与对话推出，不存字段，复制或发到应用不算（`CueStore.childMarks`）；状态点读的会话里在路上的请求优先于卡上记的会话（`handedSessions`）；提示词交给会话时它的任务也关联到那个会话、置为进行中；完成圈（`TaskRing`，一处规则）没有下级是普通圆圈，有下级时圈里画进度：按已回复的提示词与完成的子任务占的比例填一个从 12 点顺时针的扇形，进行中另在左半铺一层淡色（不用淡圈上描一道弧：小尺寸下就是系统的加载转圈）；任务行写"N 条提示词 · M 已回复"（`PromptTally`），全部回复后行尾出现"完成"，任务不自动完成、由用户确认。不做截止日期、优先级、提醒 |
| 活动 | Agent 会话（Mac 上的 Pi 会话）的历史索引 + 实时状态，只读，不复制会话原文 |
| 归档 | 做完或不再需要的灵感与任务（`archivedAt`，连同下级）：不占列表、照样搜得到，可取回；再往后是回收站（删除，可恢复） |
| 资料 | 项目里长期参考的灵感（`Card.isPinned`，界面只叫资料）：项目页任务区下面一组、一行一条，设为资料或取消当场进出；交给 Agent 时在浮起的输入框里"＋ 选灵感"带上（作为这次消息的附件，卡片不动，选卡片的面板里本项目资料排最前），"从灵感里挑"不列资料 |
| 发送记录 | 每次"内容"的投送——说给 Agent 的话、发到应用、复制——自动记录内容快照、目标与时间，可一键重发；即自动日志。命令与设置（斜杠命令、会话设置、作答、结束、停止、绑定文件夹）不是内容，不记。交给 Agent 的总是一条灵感或提示词本身。已送达而记录没写进去时照样按已发出处理（不重发），但提示没能记下 |

投送目标有两类：**Agent 会话**（Mac 上的 Pi 会话，经扩展通道直达，支持图文，无需辅助功能权限）与**任意应用**（剪贴板 + 定向 `Cmd+V`，仅文字）。

## 架构约定

- **数据**：ID 用 UUID；灵感与任务是同一张表、同一种同步记录 `Card`：`todoAt` 为空是灵感、有值是任务（`setTodo` 只翻它，改回灵感时它的下级提到它的位置），任务三态（待办、进行中、完成）由 `startedAt`/`completedAt` 推出，交给 Agent 时任务置为进行中，灵感与任务都用 `piSessionID` 关联那个会话；手动顺序用分数索引字符串，避免多设备排序冲突；项目只有一种顺序（`CueStore.projects()`：置顶在前，其余按最近活动——项目自身、其下灵感与任务的修改、其 Pi 会话的状态变化中最晚的），在 SQL 里一处定义，所有项目列表与选择器都用它；层级只有 `parentID` 一个字段（挂在任务下的任务是子任务、挂在任务下的灵感是提示词，只有任务能当上级），结构只经 `createTask(_:under:)`、`createCard(body:under:)` 与 `moveCard` 改，Store 写入时校验（不能挂到自己的子树下、整棵子树不超过 `Card.maxDepth`（3）级），子任务跟随上级的项目（挪到别的项目的任务下整棵子树换项目；直接改子任务的项目则它离开上级成为新项目的顶层），同级的范围是同一上级下或同一项目的顶层；完成上级时没完成的子任务一起完成，删除上级时子任务按原顺序提到它的位置；`store.tasks(_:)` 组内是整棵树的先序再按状态筛，上级被筛掉（已完成、上级还没同步到）的子任务就排在上级原来的位置、按顶层显示；给用户看的任务数与完成数（书架的任务一行与项目大卡、项目页"任务 n/m"、任务页与面板的分组标题、Mac 工具栏任务钮）一律只计这样显示在顶层的任务，唯一定义是 `CueStore.taskCounts`，子任务进度与提示词计数只写在上级那一行（`childMarks`）；空白灵感（正文只有空白，`Card.isBlank`）离开编辑就不留下（记一条与写提示词都是先建一条空的再编辑，收尾只有 `CueStore.dropIfBlank` 一处），也不计入灵感数（`projectSummaries`）；项目名不能写成空的（`blankProjectName`），旧版本或同步留下的空名读出来是"未命名项目"（`Project.untitled`，读行时一处换掉）；没有文字的卡在列表里叫"N 张图"或"空白灵感"（`CardText.label`）；卡片摘要只取标题之后的第一段（`CueSummary`），卡上最多 3 行（`CardText.previewLines`），正文有链接时元信息行带第一个链接的域名；软删除只保留 `deletedAt`，项目删除时其灵感与任务随项目进回收站（由项目推导，不逐条记录来源）。设备本地偏好（主题、快捷键、自动发送、当前项目）进 UserDefaults，不进同步库。变量上次取值存在那条灵感或任务上并同步。同步记录里的枚举字段（发送目标种类、Pi 状态、投送方式与状态）读出为 `Open<已知枚举>`：其他版本写入的、本版本不认识的值是 `.unknown`，原样写回，不当成已知值；本机只写已知值。界面据 Store 的观察流重读查询，不在内存复制状态。
- **界面里的项目**：每个窗口一份项目目录 `ProjectCatalog`（有效项目按 `store.projects()` 的顺序，界面不另排、各项目的灵感数、本机代码目录，以及各台 Mac 上的目录绑定 `bindings`——项目菜单与新会话落点读它），由 `Workspace.observeCatalog` 订阅；项目名称、图标、计数、目录、⌘1–9 顺序、"移到项目"、随手记落点、新会话目录等所有项目选择器都从它同步取，页面与菜单不各自再读。目录读到前根视图不显示页面，所以进入项目页、切换项目、打开菜单的第一帧就是真实值——顶栏的标题与信息在推入时定下，推入后再改会让整页跳一下，不能等页面数据。项目操作与灵感、任务的操作各只有一份定义（`UI/Shared/Components` 的 `ProjectActions`、`CardActions`），Mac 右键、iOS 长按与"更多"共用，平台只补各自的发送；绑定与解除文件夹也在 `ProjectActions` 里（Mac 弹系统的选文件夹面板，手机弹候选页`FolderPickerSheet`，规则同一份 `ProjectFolders`）。
- **图片**：按内容哈希存文件去重，正文存附件引用。文件经 `CueStore.files` 同步写入（不经 Store actor，编辑器在主线程直接用）；附件记录（同步载体）由引用它的写入（灵感与任务的正文、投送请求、发送记录）在同一事务里为本机已有文件登记，没被引用的图片不上传。缩略图只有 CueEditor 的 `Thumbnails` 一套（编辑器与灵感墙共用、按尺寸缓存），是派生数据，不落盘不同步。
- **冲突**：iCloud 按记录同步。同一条灵感或任务离线并发编辑时保留两个版本交给用户选择，不静默覆盖。两台设备离线并发挪动可能合成环、超过三级、挂到灵感下或下级与上级不同项目：应用远端变更后按确定规则收敛（`CardLinks.repairs`：挂在灵感下的（别处改回了灵感）提到那条灵感的位置，环里 id 最小的回到顶层，挂在第三级下的改挂到第二级上，下级跟随上级的项目），改写时修改时间至少比现有的晚一毫秒，各设备算出同一结果并推送；上级还没到（乱序）的不动。
- **编辑器**：存储格式是纯字符串，唯一事实源——分割线为独占行 `---split---`（只是一条线，发出去写成 `---`），图片为行内 `![](cuepad://img/<哈希>)`；运行时二者各为 U+FFFC + 附件，保存只经序列化，编辑器内复制输出存储格式。变量高亮用 `NSTextLayoutManager` 渲染属性（不写 storage、不进 undo），监听 `didProcessEditingNotification` 以覆盖输入法组合期。**禁止访问 `NSTextView.layoutManager`**（会永久降级到 TextKit 1）。附件只挂降采样缩略图并按视口懒加载，原图留在文件。iOS 另写粘贴/拖入委托、光标规范化（改写 `selectedTextRange`）与工具栏"插入分割线"按钮。选中文字时：Mac 底栏的发送只发选中的部分并多一个"转为任务"，右键菜单同样两项；iOS 编辑菜单里是"交给 Agent""转为任务"，键盘上方的发送也只发选中的部分；转为任务每行一个（去掉列表符号与复选框），归这条灵感的项目。
- **Pi 桥**：扩展随 App 打包，首次安装前征得一次同意后写入 Pi 扩展目录（要求 Pi ≥ 0.84.4）；拒绝过就不再询问、不安装；已装的是 CuePad 的扩展时，App 启动发现它与随包版本不同就静默升级（原子写入，失败进启动问题）。实时状态只在内存，历史只来自 Pi 会话文件（只读新增字节，只取会话摘要：名字、工作目录、首条用户消息（标题规则与活动会话同一处：`PiSessionName`）、最后活动；检查点不含正文，存进 Store）。协议、多客户端、版本与已知边界以 CuePi README 为准。**协议不做版本协商**：每次升级协议号，协议号不同的会话（Mac 升级扩展文件后，升级前开着的 Pi 仍加载旧扩展）整体不再读状态、不发命令，但它没死：以状态 `incompatible`（界面"在线 · 需要 /reload"）出现并同步到手机，回复框不可发并写原因，会话页顶部写明怎么做（在终端里对这个会话执行 /reload：Pi 重新载入扩展，同一会话、同一进程以新协议重连，已用真实 pi 验证）。否决的方案是按能力向下兼容旧协议——要长期维护多套行为，而升级后在终端里 /reload 就能解决。Mac 启动时静默升级扩展，已开的 Pi 会话在终端里 /reload 才用上新扩展。
- **发给 Pi**："直接发送"支持文字 + 图片与 steer/followUp；"放进输入框"只有文字，用 `pasteToEditor`（`setEditorText` 会覆盖用户已输入内容），含图片的灵感只能直接发送；iOS 回复框能自己选图与带上灵感或任务，Mac 回复框与菜单栏稿纸仍只发文字加灵感。图片发原图，Pi 自行缩放（最长边 2000px、base64 ≤ 4.5MB）。发送方式是 Store 里类型化的 `DeliveryMode`（send / steer / followUp / paste / command / answer / config / end / stop / bind / ping / start / transcript，唯一定义；bind 是请 Mac 给项目绑定文件夹（或解除）：手机看不到完整路径，正文 `PiBind` 只指名"从哪里取"（某个会话的工作目录，或另一个项目已绑的目录，`PiFolder`），Mac 解析成路径、检查目录在，写本机的目录绑定（`setDirectory`，绑定的唯一写入，Mac 上的选文件夹面板也是它；会话归哪个项目写在会话记录上，所以同一个事务里把本机已有的会话——含几千条历史，同一目录只算一次、只改归属变了的——按新的绑定重新归，绑上立即进项目、解除立即放出去），不写发送记录；按项目 id 记，项目记录晚到这台 Mac 也对得上；失败带原因写回；command 是斜杠命令，正文是以 / 开头的整行，Mac 执行器交给桥的 `command`（Pi 派发：内置命令由扩展调 Pi 接口做，扩展命令、提示词模板、skill 经 `sendUserMessage(…, {expandPromptTemplates: true})` 展开执行，不是当文字发出；忙时按等它做完再说），不是"你说的话"：不在对话里挂气泡、不写发送记录、不算发给会话的话（与 config、answer 一样；带着卡片时只把卡片关联到会话，`CueStore.linkCard`）；它的进度只在回复框上方一行短暂显示（`MacDelivery.commandProgress`：在路上"正在执行 /compact…"，没成功写原因，成功就消失）；结果若在会话文件里（压缩、模板与 skill 展开出的那条用户消息）对话里自然有——对话只来自会话文件，与终端里看到的一致，会话文件里没有的不显示（扩展命令自己什么都不写、会话名与模型与思考强度只是设置条目，这些终端的对话里也没有）；回复框与交给 Agent 输入框里输入 / 弹出的命令面板（`PiSlashPalette`，规则 `PiSlash`）列的是会话上报的清单（`PiSessionState.commands`），清单里的名字才发成 command，其余当普通文字；能做与做不到的内置命令见 CuePi README；transcript 是请 Mac 从会话文件补写一个会话的对话，正文是会话 id，不写发送记录）。**Mac 在后台托管 Pi**（`CuePi.PiHost`，`pi --mode end，不写发送记录、不算发给会话的话（会话的显示状态不把它算进去），Mac 执行器：会话不在本机桥上就按已结束、成功写回，不恢复它；在桥上的，后台托管的关标准输入、开在终端里的走扩展的 end 命令，10 秒内没退出按失败写回；结束的进度只来自发给该会话的结束请求（`DeliveryRequest.shownEnd`，CueStore 里一处，会话页与 Agent 页共用，Agent 页经会话列表的 `ends` 读，界面不另存状态），`requestEnd` 遇到还在路上的结束请求就返回它、不写第二条；stop 是停止这一轮（相当于在 Pi 里按 Esc），正文固定为 stop，同 end 不写发送记录、不算发给会话的话，`requestStop` 同样复用还在路上的那一条；Mac 执行器：会话不在本机桥上按成功写回（不恢复它），在桥上的交给扩展的 abort 命令（`PiBridge.abort`，立即 ack，不等歇下）：取消等你确认的弹窗、中止指挥官正在跑的回合，会话随后以"被中止"歇下（状态记录里是完成）、能接着说，空闲时什么都不发生；只停指挥官自己这一轮，FireCode 子代理不受影响，等子代理（`delegating`）时没有这一轮可停，所以界面只在 `isTurnRunning` 时给入口；ping 是连接测试，Mac 执行器收到即按成功写回、不碰目标与 Pi、不写发送记录，iOS 设置·同步的"测试到 Mac 的连接"连发 10 条，看往返与三段（上传、到 Mac 执行完、回到手机；后两段用 Mac 写回的完成时间，跨设备时钟）的中位数），Mac 界面的发送目标与投送请求都用它，只在调用 Pi 桥时落成桥的 steer/followUp。**发给 Pi 只有投送请求一种记录**：Mac 上发给 Pi 会话（会话页的回复框、灵感与任务的发送按钮、菜单栏稿纸）也是写一条指定本机 `hostID` 的投送请求，由本机执行器与手机发来的请求同一流程执行——送达、写发送记录、带任务时把任务关联到该会话（`recordSend` 同一事务）——发起的界面等结果再提示；直接发送而会话正忙时不写请求，先问马上说还是等它做完再说；发给应用、复制到剪贴板仍直接执行。手机经同步下发的投送请求里读到本版本不认识的值时原样保留、Mac 不执行、按失败写回，不静默当成已知值。失败原因一律读 `DeliveryRequest.failure`：执行器写回只接受成功或带原因的失败，别的版本写来、没带原因的记录读出唯一的兜底"Mac 没有说明原因"，界面不再各写一句。
- **投送**：进程内 `Dispatcher` actor，经前台应用/剪贴板/按键三个协议接缝测试。顺序靠任务链而非 actor 本身（actor 在 await 处可重入）。激活先订阅通知再调用，超时报错不发键；目标未运行时报错且不动剪贴板。单条目同时放文字与 PNG 时，图形应用只取其一，所以含图的灵感写成按原顺序含图的 RTFD 并附纯文字兜底。辅助功能授权归属 CuePad.app。窗口隐藏与发送记录由调用方负责。
- **命令行**：`cuepad` 随 App 分发在 `CuePad.app/Contents/Helpers/cuepad`，由 `CuePadCLI` 目标统一构建、随 App 签名与公证。设置里"命令行"一节的开关在 `~/.local/bin/cuepad` 建符号链接（位置被别的文件占用时不覆盖，App 被移动后能检测并一键修复；不做需要提权的 /usr/local/bin）。它与 App 用同一套资料库位置规则。
- **测试**：Swift Testing 覆盖 Store、同步映射、Pi 会话解析与桥协议、投送队列、命令行；另有"构建 → 运行 → 截图"的视觉验收流程。测试只用替身或不产生按键事件的系统调用，不向其他应用发送键鼠事件；服务测试用临时目录、独立 UserDefaults 与记录型替身，不碰真实资料库、`~/.pi` 和其他应用。全局热键的物理触发与跨应用粘贴只能人工验证。

## 同步

主 App 启动时创建 `CloudSync` 并启动：两个入口（Mac 的 `AppDelegate`、iOS 的 `Launch`）都以 `sync: .iCloud` 构造 `AppServices`，由 `AppServices.makeSync` 按位置与本构建的 iCloud 权限决定（隔离模式 `CUEPAD_LIBRARY_DIR` 与没有 iCloud 权限的本机构建不创建引擎）；该参数没有默认值，测试用 `.custom(替身)`。没有引擎或引擎没能启动时 `syncStatus` 是写明原因的 `.unavailable`，引擎确认账号前是 `.starting`，界面不会显示成"已同步"；未登录 iCloud 或关闭了本 App 的 iCloud 显示 `.noAccount`，文案告诉用户去哪打开（`SyncSummary`）。Mac 启动时注册远程通知，引擎才能收到别的设备改动的静默推送；回到前台、Mac 系统唤醒时立即 `syncNow()`，推送由引擎自己处理。静默推送按低优先级投递，不保证送达与时效；而 CKSyncEngine 只拉它已知"有变化"的 zone（名单只由推送、切到前台与"太久没拉"填上），没有推送时手动 `fetchChanges`（含限定 zone 的写法）不发任何请求。所以手里有正在等的东西时由 `SyncPoller`（CueSync，输入是此刻的拉取节奏，nil 表示不在等）开始在等时立即、之后按节奏调 `CloudSync.pullChanges()`：`ZoneChangePuller` 不经引擎、直接拉同步区的变化（`CKFetchRecordZoneChangesOperation`），交给协调器与引擎同一个 `.fetched` 合并入口（幂等）；令牌只在内存，第一次只带版本与状态（`modifiedAt`、`state`、`status`）把令牌推进到现在（其间看到的"在等的表"——投送请求与 Pi 会话状态——本机已有的只在服务器上较新时补取，本机没有的只补取还没完的（已结束的会话——几千条历史——与已有结果的投送请求由引擎带来），按 ID 每次至多 400 条（CloudKit 单次请求上限）取整条交给协调器，补取完成才记下令牌，不被令牌跨过），过期则重取，持久的权威仍是引擎状态。节奏只在 `AppServices.pollingCadence` 定义：Mac 桥上有 Pi 会话连着（以桥为准）或有本机要执行的投送请求时每 2 秒；手机有还没结果的投送请求时每 2 秒、每次在等最多 2 分钟，正在看 Agent 页或会话近况时每 3 秒，进入后台即停、回前台恢复。手机写出投送请求（发送、作答、连接测试）后、Mac 执行器写回结果后，都立即只上传这一条（`CloudSync.sendNow`），不等引擎的自动调度（Mac 上相邻两次自动上传可相隔二十多秒）。推送仍是主通道。`CloudSync.stateUpdates` 推送"状态 + 问题"快照（状态不变时新增或重复的问题也送达），`AppServices` 据此暴露 `syncStatus`、`syncIssues`，另有 `conflicts` 与 `resolveSync`、`resolveConflict`。待推送的登记由数据库推导：启动、处理同步决定时全量对账；之后每次本机提交只登记这次改动的记录（SQLite update hook 记下的改动行）；别的进程（命令行）写过库、或有登记因配额等失败被搁置时，下一次改动全量对账；`syncNow`（回到前台）先按数据库重新登记再发送。CloudKit 一批记录整体提交：一条被拒，同批其余以 `batchRequestFailed`（22）失败，引擎不替它们重试，所以同步逻辑把它们重新登记；冲突里本机版本胜出时同样重新登记；真正被拒的进问题列表，下次改动时重试。Mac 端把 Pi 会话写成同步记录，一个会话一条（记录 id 由 Pi 的会话 id 算出，重启、恢复不变）：在线会话的状态、待确认的问题、是否后台托管、子代理列表（名字与此刻在干什么，加密字段里的 JSON）与当前模型、思考强度、可选的模型（`model`、`thinking`、`models`，加密字段；`models` 在会话结束时清空）、上下文余量（`context`，已用 token 上报，不吞掉（请求会停在原状态，手机那边一直等）。投送请求的往返时间（`DeliveryRequest.roundTrip`，创建 → 结果回到本机）由发起的设备在应用远端结果时用本机时钟记下，存在同步表的本机列里，不进 CloudKit。

**结构基线**：本地库以结构 17 为基线（`Schema.baseVersion`；此前没有正式发布，更早的结构不再升级）；当前结构 18（会话记录加 `context`、`commands` 两列，见 `Schema.upgrades`）。以后改结构：在 `Schema.upgrades` 末尾追加一步并同步改 `create`；升级里任何会因数据冲突失败的语句都会让启动失败，要考虑别的设备已经同步来的数据。

**Agent 锁屏通知**：Pi 会话状态记录带明文可查询的 `notify` 标志（"等你确认"、"完成"的转换那一次写入上置位）。它是一次性事件标志，只存在于未上传的版本上：服务端接受上传即清（`CueStore.markPushed`），远端带回的 `notify` 一律不收（含自己上传的回声）；带标志的写入由 `PiStateRecorder.update` 返回，Mac 据此立即上传这一条（`AppServices.upload`）。CloudKit 服务端订阅在标志置位时直接生成可见通知，不依赖静默推送与 App 在后台运行；订阅由 iOS 在启动、账号变化和每次回到前台确保（幂等），结果是 `SyncState.alerts`（off / active / failed(原因)），失败不抛、状态带上服务端的原因，每次回到前台重试；点通知路由到对应会话。"要不要提示"只有一条规则 `PiAlert.entering`（进入等你确认；从工作中进入完成；首次看到的会话不提示），Mac 置位标志与手机前台的 App 内横幅（见「iOS / iPadOS」）都用它；App 在前台时系统通知不展示，由横幅负责。服务端发出的只是本地化 key 的通用句（标题与详情是加密字段，服务端看不到）；订阅带"可改写"标记，iOS 的通知服务扩展（`App/NotificationService`，目标 CuePadNotify，`com.sugeh.cuepad.notify`）收到后用记录 id 从同一容器取回记录、在设备上解密，改写成"会话名 在等你 + 问题首行"或"会话名 + 完成了"（`CueSync.PiAlertText`），取不到就保持通用句。通知反映服务端收到记录那一刻的状态：标志在上传前被状态已前进的后续写入取代就不送出，同状态的更新则沿用标志——状态记录不是事件日志，要保证每个事件都送达需要单独的追加式通知事件记录，那是另一种设计。该字段的可查询索引由生成的数据结构声明，已部署到生产环境。

### 排查与真机验证

**崩溃诊断**：`Diagnostics`（iOS 与 Mac 启动时开始）订阅 MetricKit，系统交来崩溃、卡死、CPU 与磁盘写入异常的诊断（一般在下次启动或隔天）时，把原始 JSON 按时间命名存进资料库目录下的 `Diagnostics/`（`DiagnosticArchive`，只留最近 10 份，同一份重复送达只存一份；一个包同时带多类诊断时按 崩溃→卡死→CPU→磁盘 取第一种命名与显示），不联网、不上传。设置里有诊断时多一行"上次崩溃 · 时间"（`LastCrashRow`），点开看摘要（异常类型、信号、终止原因、崩溃线程顶部的帧，未符号化、靠 dSYM 还原）并"导出诊断"（复制到剪贴板，与"读不出资料库"页同一个 `ExportDiagnosticsButton`）——真机崩溃拿不到栈时，请用户从这里导出发来。隔离库（`CUEPAD_LIBRARY_DIR`）不订阅。验收：`-CuePadSampleCrash YES` 存一份样例（配 `-CuePadCrashSheet YES` 直接打开摘要）；点通知后的路由用 `-CuePadScene notifytap` 与 `-CuePadColdTap` 看（见 `DebugScene+iOS` 注释，它们绕过了系统的代理回调）。系统回调约束：带完成块的 async 代理方法（`UNUserNotificationCenterDelegate` 等）必须留在主 actor、不标 `nonisolated`——编译器生成的转接在方法所属的 executor 上调系统交来的完成块，后台线程调用时 UIKit 在块里断言主线程而崩溃（真机点锁屏通知进 App 的崩溃，由 `PiAlertRoutingTests` 经 Objective-C 选择器像系统一样调用来守）；回调里只做取值与记下，不 await 别的。

App 自己的日志都在 subsystem `com.sugeh.cuepad`（类别 `services`、`launch`、`shutdown`、`pi-history`）；CloudKit 与 CKSyncEngine 的日志在 `com.apple.cloudkit`：

```bash
log show --last 30m --info --debug --predicate 'subsystem == "com.sugeh.cuepad" OR (process == "CuePad" AND subsystem BEGINSWITH "com.apple.cloudkit")'
log stream --info --predicate 'process == "CuePad" AND subsystem BEGINSWITH "com.apple.cloudkit"'   # 实时看
```

引擎日志里的错误详情是 `<private>`，看不到原因。要复现：拿用户库的副本、清掉引擎状态，用真实的同步代码在带生产签名的最小程序里跑一遍、读问题列表——它会真的上传副本里的待推送记录，只在确认副本内容就是用户本机那份时做。

同步是否真在跑，以库为准（只读复制出来看，不碰用户的库）：`syncState` 有一行 `engine`（引擎序列化的状态），`syncRecords` 的行数随推送增长到与同步表记录数相当。真机验证：装发布版 → 打开设置的同步分区，应先显示"正在连接 iCloud…"再变"已同步"（未登录或关掉本 App 的 iCloud 时显示去哪打开）→ 几分钟内复制库检查上面两张表 → 另一台设备上能看到同一批项目、灵感与任务。验证生产环境的订阅能否创建：用 Developer ID 描述文件签名、带 production 容器权限的最小 Mac 程序保存订阅，打印完整的 CKError（看 `description`，`localizedDescription` 会丢掉服务端的说明）；开发环境的 Mac 描述文件按 Provisioning UDID 登记设备，不是 Hardware UUID。

### CloudKit 数据结构

数据结构由同步记录映射推出，不手写：`apple/CloudKit/cuepad.ckdb` 是生成物，`CloudKitSchemaTests` 保证它与映射一致；映射改了测试会失败，在 `apple/CuePadKit/` 下用 `CUEPAD_REGENERATE_SCHEMA=1 swift test --filter regenerateSchemaFile` 重新生成，再导入开发环境。管理令牌存在钥匙串 `cuepad-cloudkit-management-token`，不入库、不打印：

```bash
export CLOUDKIT_MANAGEMENT_TOKEN=$(security find-generic-password -a cuepad -s cuepad-cloudkit-management-token -w)
C="--team-id SVPPQJM9JG --container-id iCloud.com.sugeh.cuepad --environment development"
xcrun cktool validate-schema $C --file apple/CloudKit/cuepad.ckdb
xcrun cktool import-schema $C --validate --file apple/CloudKit/cuepad.ckdb
xcrun cktool export-schema $C --output-file /tmp/dev.ckdb   # 回读：服务端把字段按字母序排列并补系统字段，逐类型核对字段与权限
```

开发环境的结构已导入并回读核对，生产环境已部署（含 `piSessionStates` 的 `model`、`thinking`、`models`，回读与开发环境一致）。生产环境的结构只能增不能删，开发环境导入的结构也不能删去生产已有的字段与类型：已下线的记录类型 `tags`、`cardTags`、`probes`、`tasks` 与字段 `cards.isFavorite`、`cards.numbering`、`projects.goalCardID`、`projects.sortKey`、`sendRecords.taskID`、`deliveryRequests.taskID`、`sendRecords.partIDs`、`deliveryRequests.partIDs` 在生成器里（`CloudKitSchema.retiredTypes` / `retiredFields`）照原样声明，客户端不再读写（`partIDs` 生产环境若还没部署也不必部署）；灵感与任务合并在 `cards` 上新增的 `parentID`、`todoAt`、`startedAt`、`completedAt`、`piSessionID` 与 `projects.intro` 已部署到生产环境（回读与开发环境一致）。`cards.archivedAt`（INT64）、`piSessionStates.context`、`piSessionStates.commands`（均为加密字符串，上下文余量与斜杠命令清单）已导入开发环境并回读，生产环境待部署（发布带这些字段的版本前必须先在控制台 Deploy Schema Changes：生产容器里写未部署的字段会让整条记录保存失败，Agent 会话状态就同步不上去）。生产环境只能在 CloudKit 控制台网页点「Deploy Schema Changes」部署开发环境的结构，所以映射再改时需重复"生成 → 导入开发环境 → 控制台部署"。订阅也是 schema 的一部分，但不在 `.ckdb` 里，cktool 看不到也导不出：生产环境拒绝客户端创建没部署过的查询订阅（CKErrorDomain 12，底层 BadSyntax 2006，服务端原文 attempting to create a subscription in a production container），区域订阅与数据库订阅不受此限；订阅类型按通知形状匹配（换成 alertBody 的变体会被拒）。所以改订阅的定义（谓词、选项、通知文案 key）要先让开发环境签名的构建在开发容器里保存同样的订阅，再在控制台 Deploy Schema Changes——确认页的 Record Types、Indexes、Security Roles 都显示 0、也不单独列出订阅，但部署照样生效。

## 平台

### macOS 壳层

主窗口在 `MainWindowFactory` 创建时就设好外框（内容铺到透明标题栏下），界面不要再在运行时改窗口样式；设置窗口（⌘,）由 `SettingsWindowController` 承载；`CuePadApplication` 在退出前结束挂在窗口上的弹窗，⌘Q 与 SIGTERM 才不会被 sheet/alert 卡住；退出时先等服务收尾（停止远程投送执行器、同步引擎、Pi 连接与全局快捷键）再放行，整体最多等约 2 秒，卡住的组件不拦着退出、记一条 `shutdown` 日志指出是哪个；收尾的等待不在主线程上、回复经主 run loop 的 common modes 送达（`terminate` 可能是在主线程上的任务里调用的，那时系统在嵌套事件循环里等回复，主线程上排队的任务轮不到），所以同步引擎等组件的接口不能隶属主线程（`SyncControlling` 是 `nonisolated`）；菜单栏面板 `MenuBarPanel` 随内容尺寸变化，顶边固定在图标下方。单元测试以 App 为宿主，宿主检测到 `XCTestConfigurationFilePath` 时不启动壳层，避免注册真实全局热键和菜单栏图标。

### iOS / iPadOS

- 资料库在 App Group 共享容器 `group.com.sugeh.cuepad` 的 `Library/`（库文件、`Attachments/`、待入库的 `Capture/`、给小组件的 `Snapshots/`），偏好用同名 UserDefaults 套件。模拟器直接可用；真机需要开发者账号给三个目标（App、分享扩展、小组件）签上该 App Group。
- 资料库始终只有主 App 写：分享扩展把内容放进 `Capture/`，主 App 在前台、收到扩展的进程间通知时入库；小组件与扩展不打开资料库，只读主 App 写的 JSON 快照。
- 每个窗口（iPad 多窗口）各有一个 `SceneContext`，选中项目不放进全局偏好。
- 有同步时，每个窗口出现后请求通知权限并注册远程通知（`Info.plist` 声明 `remote-notification` 后台模式）；权限状态在 `PiAlertCenter.authorization`，每次回到前台刷新，推送注册结果来自 `IOSAppDelegate` 的两个注册回调；设置页"Agent 通知"一行由 `PiAlertStatus` 从权限、注册、订阅三步里选出卡在哪一步（通知被关给"打开系统通知设置"，未决给"开启通知"，失败只写人话说明与"重试"，底层原因折叠在"详情"里；演示截图用 `-CuePadAlertStatus`）。设置页同步一节的写法同 Mac：同步出错时状态只说人话（有记录没能上传，本机的内容都在，回到前台会自动重试），底层原因折叠在"没能同步"的明细里，每条按记录类型说明是哪一类（`SyncIssue.summary`）。锁屏通知文案（"Agent 在等你确认" / "Agent 完成了"）按 key 取自 `App/Sources/zh-Hans.lproj/Localizable.strings`。前台不展示系统通知（`willPresent` 返回空），前台的提示是 App 内横幅：`AppServices.startSessionAlerts` 观察本机已同步来的在线会话，`SessionAlertTracker` 拿读到的版本与上一次比（`PiSessionState.alert(since:)`，与 Mac 置位推送标志同一条规则 `PiAlert.entering`；第一次读到只记基线，同步合并掉中间状态时按状态起点判断），认出"等你确认"、"做完了"就交给各窗口，窗口用顶部的提示横幅（`NoticeBanner`，停留 5 秒、点它进该会话；让到顶上那一排——推入页的悬浮顶栏或标签根页自己的搜索与按钮行——下面，不遮住返回钮与标题）显示；正看着那个会话（`Navigation.isViewing`：它是当前标签最上面一页，不靠进出页面的计数）的窗口不弹，App 不在前台时不发（后台走系统推送），后台期间的转换回到前台也不补报：这部分只靠系统推送，Agent 页上每个会话本来就显示当前状态。会话第一次被读到时没有上一版本，不提示（与 Mac 置位推送标志同一条规则，重新读取时不把旧事件再提示一遍）。不依赖推送是否到达。点开通知由 `Sources/iOS/PiAlertCenter.swift` 交给界面：打开该会话（iPhone 在 Agent 标签里，iPad 推入详情栏）。

- **任务菜单与浮窗**：长按（Mac 右键）菜单只在 `CardMenu` 定义，最多四项加删除——灵感是 交给 Agent、设为任务、移到项目、归档，任务是 完成/重新打开、归档（任务本身没有话可交，交给 Agent 在每条提示词上）；删除单独在最后。低频的在任务页与纸页的"⋯"里（`CardMenu.more`）：任务是 移到项目（只顶层，子任务跟上级）、复制、改回灵感、归档、删除，灵感是 设为任务、设为资料/不再是资料、移到项目、复制、归档、删除。任务页（iPhone 是七成高可拉满的浮窗 `TaskPage`；Mac 整页打开，同一组件）：顶上完成圈（`TaskRingButton`）与单行标题、一句说明（`TaskHeading`，就地改、自动保存），右上"⋯"；主体是提示词卡片（`PromptList`/`PromptCard`）：内容预览、此刻怎样（还没发的不写状态，只有"交给 Agent"；交给某会话·处理中（含手机重发还在路上的"正在发给 Agent"）/ 会话已结束（没回复就结束，可重新交给 Agent）/ Agent 已回复，点它看会话；`PromptState`）与就地"交给 Agent"（iPhone 浮起交给 Agent 的输入框，Mac 发给当前目标；只有还没发的那条是靛青的强调钮，交出去过的退成墨色文字"再交一次"），点卡打开灵感的大编辑区（顶栏写任务名与"提示词"），末尾"写一条提示词"先建一条空的、直接进入编辑，什么都没写就离开不留下（`Workspace.leaveEditing`，见「架构约定 · 数据」的空白灵感）；右上"从灵感里挑"挂一条上来；子任务在提示词之后（`SubtaskList`，没有时整组不出现；这里不加子任务，在任务大纲里把任务拖到它上面就成了它的子任务）。完成任务后提示"已完成 · 归档"（不自动归档）。完成圈的画法在 `TaskRingView`，颜色同 `TaskGlyph.tint`。
- **灵感 → Agent**：灵感右滑交给 Agent（主动作，过阈值轻触感）、左滑设为任务（未分类列表里是系统的左右滑按钮，左滑另有移到项目）；交给 Agent 浮起交给 Agent 的输入框（`HandOffInput`，与随手记、新会话同一种浮起输入框）：正文已带上（提示词卡上的交给 Agent 也是它），可补一句，"＋ 选灵感"再带上别的卡片作附件（如本项目资料，面板里排最前；卡片不动、正文依次接在后面，请求总关联为它打开的那条灵感或提示词——它在这个输入框里不能拿掉，其余附件可拿掉），工具排里是选中会话的模型与思考强度（同会话页 `PiConfigControls`），头部胶囊选"新会话…"（排最上，换成新会话的输入框，草稿带过去）或会话（本项目的在前）；Mac 的发送目标菜单在项目绑了目录时也有"新会话"（`Workspace.newSessionHandOff`），发出即收起并提示"已交给 …"。之后灵感与任务的行和卡上出现那个会话的状态点（`AgentDot`，读 `AgentLinks`：执行过的记在卡上 `piSessionID`，灵感也记；手机发出还没执行的读投送请求，`CueStore.handedSessions`；开新会话的请求带着这条灵感或任务，开好前是墨色空心点"正在开会话"，会话记录带着认领标识 `launchToken` 写下或同步到时 `claimLaunchedCards` 把它关联到新会话——Mac 记录器与同步落库同一处），随状态变化，Agent 做完是"有新回复"的墨色点，点它就是那个会话。
- **改会话名**：iOS Agent 页的长按与左滑、会话页"⋯"，Mac 侧栏与 Agent 整页的右键、会话页"⋯"里有"重命名"，弹出就地的输入框（预填现在的名字；空着或没改时"改名"停用、看得出灰，`renameSession`；用小表单的工具栏按钮而不是提示框，iOS 提示框不画按钮的停用态）。改名是会话设置，与改模型、思考强度同一条路：一条带名字的配置请求（`PiConfig.name`，`AppServices.rename`），扩展用 Pi 设置会话名的接口执行（同 `/name`），不写发送记录、对话里不出气泡、不算发给会话的话；已结束的会话 Mac 先在后台恢复再改。会话名只来自 Pi（会话记录的 `title`），不另存：会话列表查询给每个会话带最近一条改名（`PiSessionListItem.rename`），在路上或送到了而会话记录还没写过时行与会话页顶栏写新名、状态后面写"正在改名"，之后以会话记录为准；没改成回到旧名，行上写"没能改名：原因"，留到你看过这个会话为止（`PiRename`）；旧版扩展的会话收不到设置，不给改名。

- **生命周期**：活跃 → 归档（`archivedAt`，连同下级一起；不占列表、照样搜得到）→ 回收站（删除，可恢复）。归档入口：长按与"⋯"的"归档"、完成后提示里的"归档"、任务页与 Mac 任务面板"最近完成"的"全部归档"（只动已完成的顶层任务，没做完的任务下已完成的子任务留着算进度）。归档页：iPhone 书架"⋯"、iPad 侧栏、Mac 侧栏里与回收站并列（`ArchiveList`，取回连同下级回到原处，删除进回收站）。
- **底部栏**：照系统悬浮标签栏（照片、音乐：标签组靠左、圆钮靠右）的几何（与屏幕圆角同心，数值只在 `BottomBar`）；内容在安全区之上再让出栏顶以上的高度（`BottomBar.reserve`，键盘盖住栏时为 0），滚到栏后面的内容淡到页面底色（`EdgeFade`，栏的上沿往上再淡出 20）；玻璃上不铺底，选中那格是一层中性的滴（浅色压暗、深色更暗，同系统）加靛青的图标与字，未选中是墨色，"写"是同高的纯玻璃圆钮（不做靛青实心钮：一屏的焦点留给内容）；按住未选中的格亮淡按压底、按住选中格滴轻压 0.94 并轻触感（减弱动态效果时只淡入淡出）；角标比标签字小一档起步、到 xLarge 封顶（`@ScaledMetric` 的上限要加在调用处）；标签字固定不随字号，辅助字号下长按弹出大内容查看器（图标与标题）。
- **iPad**：左栏项目（项目行下面是"此刻"一行，同书架；含任务、Agent、搜索入口）、右侧灵感墙与项目页，Agent 也可在右侧面板并排看，编辑时纸页覆盖项目页；外接键盘快捷键与 Mac 对齐。

## 资料库与隔离

位置规则唯一来源是 `CueStore` 的 `LibraryLocation`：macOS 在 `~/Library/Application Support/CuePad/Library/`，iOS 在 App Group 容器；环境变量 `CUEPAD_LIBRARY_DIR`（必须是绝对路径）指向隔离目录，资料库、偏好设置（主题、快捷键、当前项目、窗口位置）都放进去，不碰真实的 `com.sugeh.cuepad` 偏好域，并行实例互不影响。App、命令行与测试都经它取位置。

资料库打不开（更早或更新版本建的库、损坏）时不终止进程：唯一入口 `AppServices.openLibrary(at:)` 抛出 `LibraryFailure`（原文、路径、结构版本、是更早还是更新版本建的），iOS 与 Mac 都显示 `UnreadableLibraryView`：人话说明、折叠的详情、重试、导出诊断（复制原因、路径、结构版本与本版本支持的版本、App 版本）；没有任何写入入口，打不开也不会换成空库；项目目录读取失败的页面（`CatalogGate`）用同一个组件。位置本身有误（没有 App Group 权限、`CUEPAD_LIBRARY_DIR` 不是绝对路径）时，iOS 同样走这一页，Mac 仍提示后退出；Mac 上打开失败弹一个独立的失败窗口，重试成功后自动关闭。

## 视觉验收

`shot mac` 直接启动产物里的可执行文件并记下它的 PID（不经 LaunchServices 激活，不抢焦点；上次中断遗留的实例只按记下的 PID 结束），按该 PID 找窗口 ID 后 `screencapture -l` 只截该窗口（首次需给终端授予屏幕录制权限）；以 SIGTERM 退出，走应用正常退出流程。`shot ios` / `shot ipad` 构建 → 模拟器安装启动 → 截图 → 终止，库与偏好放进 `.derived/library-ios`。`--` 之后是 App 启动参数：

```bash
apple/scripts/xc.sh shot mac out.png -- -CuePadDemo YES -CuePadScene editor -theme dark
```

- Debug 构建认一组启动参数：`-CuePadDemo YES` 空库时写入演示数据，`-CuePadProject <名称>` 打开该项目，`-CuePadScene <画面>` 选初始画面，`-CuePadBench`、`-CuePadSeed perf` 给性能测量与压测用。参数的完整列表与含义只写在 `App/Sources/UI/Debug/DebugScene.swift`（共用与 Mac）和 `DebugScene+iOS.swift`（iOS 的画面名）的文档注释里；设置项可直接覆盖（`-theme dark`）。`settings`、`menubar` 画面把设置窗口、菜单栏面板的内容放进主窗口拍，因为只截主窗口。
- `CUEPAD_SHOT_LIBRARY` 换库目录（默认 `.derived/library`），`CUEPAD_SHOT_SETTLE` 是出窗后等待渲染的秒数。
- Pi 目录同样隔离（`.derived/pi-agent`、`/tmp/cuepad-shot-<uid>`），截图不含 `~/.pi` 的会话。隔离的 Pi 目录里没装扩展，侧栏底部出现"连接 Pi"征求同意是正确状态；不要它时传 `-piExtensionDeclined YES`（只写入参数域，不改已保存的设置）。
- 布局反馈环压力场景：`apple/scripts/layout-stress.sh [CuePad.app]`（缺省取 `$CUEPAD_DERIVED` 的 Debug 构建）跑三组隔离实例——屏幕外最小窗口下 Pi 会话快速结束/新建并在思考中/出错间跳、1280×907 下 Pi 全状态轮换、常驻滚动条下边加灵感边拉宽，本机有真实 pi 时再加两组真实 Pi 会话「发提示词 → 出错/完成 → 开新会话 → 立刻再发」（`apple/scripts/pi-real-churn.py`，离线假模型 `pi-stress-model.ts`，每轮等上一轮结束再开新会话，会话文件真实落盘，并断言 Pi 会话文件与应用历史确实产生、否则判为没覆盖到）——按进程日志里的 "Geometry action is cycling" 与 "has continued for 300 iterations" 判定，有则退出码 1。检测器自检：`layout-stress.sh --inject-loop` 给每组挂上刻意的几何回写环（`-CuePadGeometryLoop YES`），必须以 1 退出，证明它抓得到这类环。Pi 轮换由 `apple/scripts/pi-churn.py` 假扩展提供。界面约束：工具栏内容只随用户操作与数据变化，不随滚动位置、尺寸等布局读数变化；几何读数（`onGeometryChange` / `onScrollGeometryChange`）不写回影响自身排版的状态，按宽度切换排版用 `Layout` 或 `ViewThatFits` 当场决定；推入页的底色铺在导航容器上（`containerBackground(_:for: .navigation)`，iOS 在推入路由的统一入口 `RouteView` 一处铺），不铺在滚动区上，否则数据没到的几帧整页透明露出系统黑；顶栏的工具栏项在推入时就建好、之后只换其中的内容，控件随数据置灰而不出现消失（推入转场期间系统不重建工具栏项，换项要等转场结束才显示，纸页的标题会晚到近一秒）。
- 性能测量：`apple/scripts/perf-mac.sh [次数]` 构建打开编译优化的 Debug（测量代码只在 Debug 里），第一次在隔离库里写入合成大库（50 项目、5000 条灵感其中 300 条带 4032×3024 大图、200 个 Pi 历史会话、500 条发送记录），之后每次冷启动跑 `-CuePadBench perf`，输出一行 JSON：冷启动到首屏灵感出现、内存（phys_footprint）、项目页滚轮快速上下滚（每帧 40pt）、开合纸页与开合侧栏 10 次的帧间隔、⌘K 每个关键词的 Store 查询中位数与打开面板到结果读到。Agent 整页用 `-CuePadBench agent`（同一种构建，库指向真实库副本）：打开 Agent 整页用滚轮一路滚到底（读到底接着分页），输出往下滚的帧间隔、用时与前后内存。帧间隔的口径：主线程上 display link 两次回调之间的时间（`hitchesAt` 列出每次超过刷新间隔 1.5 倍的位置与时长），反映主线程跟不跟得上，不是画面实际交出的帧率——渲染服务一侧的节奏也会推迟回调，画面没在动时的长间隔用户看不到。是否真的掉帧以 Instruments 的 Animation Hitches（`--template 'Animation Hitches' --attach <pid>`，看 hitches 表的时长与"app update / render"归因）为准；定位主线程开销用 Time Profiler，看主线程在等什么用 System Trace 的线程状态。Animation Hitches 在 iOS 模拟器上不支持（报 "Hitches is not supported on this platform"），iOS 端用模拟器录屏逐帧或应用内每帧探针取证。窗口在后台也能测（display link 照常走），不用抢前台；但窗口得在屏幕上：放到屏幕外（`-CuePadOffscreen`）时 display link 不走，帧间隔与 Animation Hitches 都测不到，屏幕外只用于布局与日志类场景。界面约束：点开纸页的那一格点下即按下（`CardOpenStyle`，0.98）——按下由主窗口的本地事件监听在 AppKit 分发鼠标按下时记到这一格上（鼠标停着的那一格，早于 SwiftUI 按钮识别），点下那一帧直接缩到 0.99、余下再缓动（动画第一帧进度为零），松开稍等 80ms 再放开（打开中接上就不弹）；准备期间由它自己保持按下（开合阶段 `opening`），纸在开始放大的那一帧以按下的样子接过它；会动的过渡里，重活（创建编辑器、挂底栏、让编辑器接过键盘）放在动之前、每帧一步（等屏幕下一次刷新再做下一步，主队列异步可能挤回同一帧），动起来之后每帧只剩动画与改透明度；大容器（主窗口）的视图体不读开合这类频繁变化的状态，读它的部分拆成小视图；大量行的区域用懒加载栈，懒加载栈里一组行的容器也要懒加载（Agent 整页历史分组曾用普通 VStack 垫纸，三千条历史滚到底内存到 1.4GB、每读一页卡一两秒；"更早"上千行全建出来时，每个滚轮事件的命中测试与每帧布局都按行数增长）；灵感墙的每一格不读整窗共享、随开合变化的状态，开合状态按格分开（`CardPresence`），位置读数只在它被打开期间挂上；卡片上不用渐变描边（`strokeBorder(LinearGradient)` 由 CPU 按整张卡的面积铺渐变，卡片一变宽整面墙都要重画：大库里开合侧栏的第一帧曾因此卡到约 150ms），渐变只用在填充上。侧栏开合的帧耗时大头在 AppKit 分栏自己：收放动画每帧整窗重新布局、重算标题栏拖动区（逐个询问页面里的视图），空详情区、空侧栏时 144Hz 下每 10 次开合仍掉约 25 帧；页面在动画里只被推着走、不重排（`PinnedPage`）。试过页面不进侧栏让出的安全区、改由动画平移（与侧栏同步），每帧照样要移动滚动区并重算拖动区，掉帧不比被推着走少，没有采用。
- 窗口位置/尺寸会被系统记住（`NSWindow Frame main`），截图尺寸以上次为准；恢复默认：`defaults delete com.sugeh.cuepad "NSWindow Frame main"`。

## 签名与发布

本机构建走 ad-hoc 签名（`xc.sh` 覆盖工程默认的团队与身份，并换用不含 iCloud/推送的 macOS 权限文件）；签名事实源是 `App/Config/Signing.xcconfig`。发布与真机构建是手动签名：Xcode 的自动签名用 API 密钥时管不了 App Group 与 iCloud 容器，所以证书与描述文件由 `scripts/provision.py` 经 App Store Connect API 创建，工程里各 target 指定名称（只对 `iphoneos` 与 macOS 的 Release 生效，模拟器与日常构建不受影响）。

凭据文件 `~/.appstoreconnect/cuepad.env`（不入库）的字段：`ASC_KEY_ID`、`ASC_ISSUER_ID`、`ASC_KEY_PATH`（App Store Connect API 密钥 `.p8` 的路径）、`CUEPAD_TEAM_ID`；`xc.sh release ios` 另需 `CUEPAD_TESTER_EMAIL`（加入内部测试组的 App Store Connect 用户邮箱）。Apple Distribution 证书的私钥放专用钥匙串 `~/.appstoreconnect/cuepad-signing.keychain-db`。缺凭据文件时 build/test/shot 照常，只有下面的发布命令会报错；密钥内容不会打印。

| 命令 | 作用 |
| --- | --- |
| `xc.sh provision` | 幂等：创建 App ID 与能力（App Groups、iCloud、推送）、Apple Distribution 证书、iOS 与 macOS 描述文件 |
| `xc.sh release mac` | 刷新描述文件 → 归档（Developer ID）→ 导出 → `notarytool` 公证 → 装订 → `spctl` 与 `codesign` 校验 → `<产物目录>/release/mac/CuePad-<版本>-mac.zip`，并生成 `appcast.xml`（见「自动更新」） |
| `xc.sh release ios` | 刷新证书与描述文件 → 归档 → 导出 IPA → `altool` 上传 → 建/取内部测试组「内部」并加入账号持有人（构建号取时间戳，自动递增） |
| `xc.sh device` | 登记连接的真机 → Development 证书与描述文件 → 开发构建 → 安装并启动 |
| `scripts/testflight.py builds` | 列出 TestFlight 构建与处理状态 |

权限：主 App 有 iCloud（CloudKit，`iCloud.com.sugeh.cuepad`）、推送（`$(APS_ENVIRONMENT)`：Debug development，Release production）与 App Group（iOS）；扩展只有 App Group；macOS 另有 Apple Events 自动化（终端跳转）。辅助功能权限使 Mac 版不能进 Mac App Store，走官网分发并用 Sparkle 更新。

只能在网页上做的一次性前置：App Group `group.com.sugeh.cuepad` 与 iCloud 容器 `iCloud.com.sugeh.cuepad` 的创建及挂到 App ID（主 App 与通知服务扩展 `com.sugeh.cuepad.notify` 都要挂）；Developer ID Application 证书（账号持有人创建，CSR 由 `provision.py devid-csr` 生成，`provision.py devid-import <.cer>` 导入）；App Store Connect 里的 App 记录。

## App 图标

`App/Sources/AppIcon.icon` 是 Icon Composer 的分层图标（Liquid Glass，浅色/深色/着色三种外观），由 `scripts/make-icon.py` 从品牌 logo `design/final/logo-final.png` 矢量化生成（potrace 描成 SVG，C 与纸片两层；依赖 Pillow 与 potrace）；换 logo 后重跑脚本即可，预览见 `design/final/app-icon-preview.png`。菜单栏模板图仍是 `Assets.xcassets/MenuBarIcon`。

## 自动更新（macOS）

用 Sparkle 2（EdDSA 校验、增量更新），以官方二进制 xcframework 引入：`Vendor/Sparkle/Package.swift` 只有一个 `binaryTarget`（url + checksum，升级版本改这一处），不拉 Sparkle 源码。更新源 `https://cue-pad.com/appcast.xml` 与公钥在 `App/Config/CuePad-macOS-Info.plist`；设置里"更新"一节有"自动检查更新"开关和"检查更新…"，App 菜单里也有"检查更新…"。隔离模式（`CUEPAD_LIBRARY_DIR`）不启动更新器。

EdDSA 私钥在专用钥匙串（`~/.appstoreconnect/cuepad-signing.keychain-db` 里的 `cuepad-sparkle-ed25519`，不入库；`scripts/sparkle.sh key` 首次运行时生成并打印公钥）。`xc.sh release mac` 用时间戳作构建号（Sparkle 按 `CFBundleVersion` 比较新旧，每次发布必须递增），在公证、装订后把 zip 收进更新历史目录 `~/.appstoreconnect/cuepad-updates/` 并生成 `appcast.xml`（含与历史版本的增量包，所以历史 zip 必须留在这里；它在产物目录之外，清理产物目录或换 `CUEPAD_DERIVED` 不影响），`appcast.xml` 另复制到 `<产物目录>/release/mac/`。更新包的下载地址前缀用 `CUEPAD_UPDATE_URL_PREFIX`（默认 `https://cue-pad.com/downloads/`）；更新历史目录里的 zip、增量包与 `appcast.xml` 部署到对应位置由人决定。
