# CuePad 开发文档

CuePad 是 Swift 原生应用：macOS 26+、iOS/iPadOS 27+，iCloud 同步，Pi 深度集成。Swift 6 严格并发，界面 SwiftUI，编辑器与菜单栏面板用 AppKit/UIKit。产品定位与功能见 [README.md](../README.md)；模块索引见 [AGENTS.md](../AGENTS.md)。

## 环境与命令

需要 Xcode 27。统一入口 `apple/scripts/xc.sh <build|test|shot> <mac|ios|ipad> [截图路径]`（`ios` 是 iPhone 模拟器，默认 `iPhone 17`，`CUEPAD_IOS_DEVICE` 覆盖；`ipad` 是 iPad 模拟器，`CUEPAD_IPAD_DEVICE` 覆盖），退出码即 xcodebuild 的退出码。共用 Swift 包在 `apple/CuePadKit`，直接用 SwiftPM。

```bash
apple/scripts/xc.sh build mac
apple/scripts/xc.sh test mac
apple/scripts/xc.sh build ios
apple/scripts/xc.sh test ios        # 同一测试目标，跑其中 iOS 也编译的部分（Swift Testing；摘要里的 "Executed 0 tests" 只数 XCTest）
apple/scripts/xc.sh shot mac        # 构建 → 后台启动 → 单窗口截图 → 退出，输出 .derived/shot-mac.png
cd apple/CuePadKit && swift test    # 共用包的全部测试
cd apple/CuePadKit && swift build -c release --product cuepad   # 命令行
```

构建产物在 `apple/.derived/`（自带 `.gitignore`）。**并行的 agent 必须各用一个产物目录**（`CUEPAD_DERIVED=/tmp/xxx apple/scripts/xc.sh …`，截图、隔离库、Pi 目录随之落在该目录下），共用同一个目录时构建与测试会互相覆盖而随机失败。

## 代码地图

`apple/CuePad.xcodeproj` 是一个多平台 App target（macOS + iOS/iPadOS）加分享扩展、小组件与命令行三个目标；源码在 `apple/App/Sources/` 与 `apple/App/Tests/`（文件夹同步组，增删文件不用改工程文件）：

| `App/Sources/macOS/` | 壳层：窗口、全局快捷键、菜单栏图标与面板 |
| `App/Sources/iOS/` | iOS/iPadOS 应用入口与每个窗口的根视图 |
| `App/Sources/UI/` | 界面：`Shared/`（组件、主题、规则、工作区状态）、`macOS/`、`iOS/`、`Debug/`（视觉验收场景与演示数据） |
| `App/AppGroup/`、`ShareExtension/`、`Widget/` | iOS 的 App Group 位置与快照、分享扩展、小组件 |
| `CuePadKit/` | 共用 Swift 包，见下表 |
| `scripts/` | `xc.sh` 与签名、发布脚本 |

| CuePadKit 模块 | 职责 | 平台 |
| --- | --- | --- |

| CueEditor | TextKit 2 编辑器：内联图片、分割线、变量高亮、选区动作；AppKit/UIKit 各一层宿主 | 全部 |
| CueSync | 直接用 CKSyncEngine 同步 Store 的记录；图片以 CKAsset 同步；正文用加密字段 | 全部 |
| CueDispatch | 通用投送：权限预检 → 写剪贴板 → 激活目标 → 定向 `Cmd+V` | macOS |
| CuePi | Pi 桥：扩展（随包资源）、socket 客户端、会话历史索引、终端跳转；协议与边界见 [Sources/CuePi/README.md](../apple/CuePadKit/Sources/CuePi/README.md) | macOS |
| CueCLI | `cuepad` 命令行：名词-动词（project/card/task/search/conflicts；card 管灵感与任务——`card todo` 在两者间切换，编辑、删除也在 card 下；task 只剩任务特有的状态与层级），参数里的记录写作 `<灵感或任务>`，默认文本、`--json` 给 agent；只经 Store 公开接口读写，`cuepad --help` 与各命令的 `--help` 是其唯一文档 | macOS |

## 产品模型

功能只服务一条循环：**捕获 → 打磨 → 发出 → 回看**。

| 概念 | 定义 |
| --- | --- |
| 项目 | 灵感与任务的容器，带一句可选的介绍（`intro`），没有目标卡；可绑定一个代码目录，Pi 会话与 `cuepad` 命令行按工作目录自动归入 |
| 灵感 | 唯一的内容类型：文字 + 内联图片 + `{{变量}}` + 分割线。思考、笔记、相关灵感都是灵感；提示词就是任务的正文 |
| 任务 | 要做的灵感：与灵感是同一种记录（`Card`），"设为任务 / 改回灵感"在两者间切换；可放在项目里或未分类；挂在任务下的任务是子任务、挂在任务下的灵感是相关灵感，只有任务能当上级，最多三级（任务浮窗"进展"的"＋"加子任务或灵感）；完成圈按下级分段（`TaskRing`，一处规则）：每个子任务、每条相关灵感各占一段，子任务完成、相关灵感交给过 Agent 那段就满，超过 12 段改按比例的一道弧，没有下级是普通圆圈；可交给 Agent（发给 Agent 会话，即 Mac 上的 Pi 会话）并显示那个会话的状态，完成由用户勾选。不做截止日期、优先级、提醒 |
| 活动 | Agent 会话（Mac 上的 Pi 会话）的历史索引 + 实时状态，只读，不复制会话原文 |
| 归档 | 做完或不再需要的灵感与任务（`archivedAt`，连同下级）：不占列表、照样搜得到，可取回；再往后是回收站（删除，可恢复） |
| 资料 | 项目里长期参考的灵感（`Card.isPinned`，界面只叫资料）：项目页任务区下面一组、一行一条，设为资料或取消当场进出；交给 Agent 时可一键带上 |
| 发送记录 | 每次投送/复制自动记录内容快照、目标与时间，可一键重发；即自动日志。任务交给 Agent 时可一并带上挂着的相关灵感（默认都带、逐条可取消）与本项目资料（默认不带），发出的正文是任务加选中的各条、`---` 隔开（`TaskBundle`），这次带上了哪些记在同一条发送记录与投送请求的 `partIDs` 里（不另存正文）；相关灵感"交给过 Agent"只看它自己的发送记录或某条记录的 `partIDs`（`CueStore.childMarks`），不按正文推断。已送达而记录没写进去时照样按已发出处理（不重发），但提示没能记下 |

投送目标有两类：**Agent 会话**（Mac 上的 Pi 会话，经扩展通道直达，支持图文，无需辅助功能权限）与**任意应用**（剪贴板 + 定向 `Cmd+V`，仅文字）。

## 架构约定

- **数据**：ID 用 UUID；灵感与任务是同一张表、同一种同步记录 `Card`：`todoAt` 为空是灵感、有值是任务（`setTodo` 只翻它，改回灵感时它的下级提到它的位置），任务三态（待办、进行中、完成）由 `startedAt`/`completedAt` 推出，交给 Agent 时任务置为进行中，灵感与任务都用 `piSessionID` 关联那个会话；手动顺序用分数索引字符串，避免多设备排序冲突；项目只有一种顺序（`CueStore.projects()`：置顶在前，其余按最近活动——项目自身、其下灵感与任务的修改、其 Pi 会话的状态变化中最晚的），在 SQL 里一处定义，所有项目列表与选择器都用它；层级只有 `parentID` 一个字段（挂在任务下的任务是子任务、挂在任务下的灵感是相关灵感，只有任务能当上级），结构只经 `createTask(_:under:)` 与 `moveCard` 改，Store 写入时校验（不能挂到自己的子树下、整棵子树不超过 `Card.maxDepth`（3）级），子任务跟随上级的项目（挪到别的项目的任务下整棵子树换项目；直接改子任务的项目则它离开上级成为新项目的顶层），同级的范围是同一上级下或同一项目的顶层；完成上级时没完成的子任务一起完成，删除上级时子任务按原顺序提到它的位置；`store.tasks(_:)` 组内是整棵树的先序再按状态筛，上级被筛掉（已完成、上级还没同步到）的子任务就排在上级原来的位置、按顶层显示；给用户看的任务数与完成数（书架的任务一行与项目大卡、项目页"任务 n/m"、任务页与面板的分组标题、Mac 工具栏任务钮）一律只计这样显示在顶层的任务，唯一定义是 `CueStore.taskCounts`，子任务进度只写在上级那一行（`subtaskProgress`）；软删除只保留 `deletedAt`，项目删除时其灵感与任务随项目进回收站（由项目推导，不逐条记录来源）。设备本地偏好（主题、快捷键、自动发送、当前项目）进 UserDefaults，不进同步库。变量上次取值存在那条灵感或任务上并同步。同步记录里的枚举字段（发送目标种类、Pi 状态、投送方式与状态）读出为 `Open<已知枚举>`：其他版本写入的、本版本不认识的值是 `.unknown`，原样写回，不当成已知值；本机只写已知值。界面据 Store 的观察流重读查询，不在内存复制状态。
- **界面里的项目**：每个窗口一份项目目录 `ProjectCatalog`（有效项目按 `store.projects()` 的顺序，界面不另排、各项目的灵感数、本机代码目录），由 `Workspace.observeCatalog` 订阅；项目名称、图标、计数、目录、⌘1–9 顺序、"移到项目"、随手记落点、新会话目录等所有项目选择器都从它同步取，页面与菜单不各自再读。目录读到前根视图不显示页面，所以进入项目页、切换项目、打开菜单的第一帧就是真实值——顶栏的标题与信息在推入时定下，推入后再改会让整页跳一下，不能等页面数据。项目操作与灵感、任务的操作各只有一份定义（`UI/Shared/Components` 的 `ProjectActions`、`CardActions`、`TaskActions`），Mac 右键、iOS 长按与"更多"共用，平台只补各自的发送与绑定代码目录。
- **图片**：按内容哈希存文件去重，正文存附件引用。文件经 `CueStore.files` 同步写入（不经 Store actor，编辑器在主线程直接用）；附件记录（同步载体）由引用它的写入（灵感与任务的正文、投送请求、发送记录）在同一事务里为本机已有文件登记，没被引用的图片不上传。缩略图只有 CueEditor 的 `Thumbnails` 一套（编辑器与灵感墙共用、按尺寸缓存），是派生数据，不落盘不同步。
- **冲突**：iCloud 按记录同步。同一条灵感或任务离线并发编辑时保留两个版本交给用户选择，不静默覆盖。两台设备离线并发挪动可能合成环、超过三级、挂到灵感下或下级与上级不同项目：应用远端变更后按确定规则收敛（`CardLinks.repairs`：挂在灵感下的（别处改回了灵感）提到那条灵感的位置，环里 id 最小的回到顶层，挂在第三级下的改挂到第二级上，下级跟随上级的项目），改写时修改时间至少比现有的晚一毫秒，各设备算出同一结果并推送；上级还没到（乱序）的不动。
- **编辑器**：存储格式是纯字符串，唯一事实源——分割线为独占行 `---split---`（只是一条线，发出去写成 `---`），图片为行内 `![](cuepad://img/<哈希>)`；运行时二者各为 U+FFFC + 附件，保存只经序列化，编辑器内复制输出存储格式。变量高亮用 `NSTextLayoutManager` 渲染属性（不写 storage、不进 undo），监听 `didProcessEditingNotification` 以覆盖输入法组合期。**禁止访问 `NSTextView.layoutManager`**（会永久降级到 TextKit 1）。附件只挂降采样缩略图并按视口懒加载，原图留在文件。iOS 另写粘贴/拖入委托、光标规范化（改写 `selectedTextRange`）与工具栏"插入分割线"按钮。选中文字时：Mac 底栏的发送只发选中的部分并多一个"转为任务"，右键菜单同样两项；iOS 编辑菜单里是"交给 Agent""转为任务"，键盘上方的发送也只发选中的部分；转为任务每行一个（去掉列表符号与复选框），归这条灵感的项目。
- **Pi 桥**：扩展随 App 打包，首次安装前征得一次同意后写入 Pi 扩展目录（要求 Pi ≥ 0.84.4）；拒绝过就不再询问、不安装；已装的是 CuePad 的扩展时，App 启动发现它与随包版本不同就静默升级（原子写入，失败进启动问题）。实时状态只在内存，历史只来自 Pi 会话文件（只读新增字节，只取会话摘要：名字、工作目录、首条用户消息（标题规则与活动会话同一处：`PiSessionName`）、最后活动；检查点不含正文，存进 Store）。桥协议 v3、扩展 v14，协议、多客户端、版本与已知边界以 CuePi README 为准；协议升级后旧扩展的会话连上会被拒为不兼容，Mac 启动时静默升级扩展，已开的 Pi 会话要重启才用上新扩展。
- **发给 Pi**："直接发送"支持文字 + 图片与 steer/followUp；"放进输入框"只有文字，用 `pasteToEditor`（`setEditorText` 会覆盖用户已输入内容），含图片的灵感只能直接发送；iOS 回复框能自己选图与带上灵感或任务，Mac 回复框与菜单栏稿纸仍只发文字加灵感。图片发原图，Pi 自行缩放（最长边 2000px、base64 ≤ 4.5MB）。发送方式是 Store 里类型化的 `DeliveryMode`（send / steer / followUp / paste / answer / config / end / ping / start / transcript，唯一定义；transcript 是请 Mac 从会话文件补写一个会话的对话，正文是会话 id，不写发送记录）。**Mac 在后台托管 Pi**（`CuePi.PiHost`，`pi --mode rpc`，没有终端界面，环境里带 CuePad 用的连接目录与（非默认时的）Pi 目录与 `CUEPAD_HOSTED=1`，扩展在 hello 里带回，同步记录的 `hosted`）：直接发送到这台 Mac 上已结束的会话时，执行器先用会话索引里的会话文件与工作目录在后台恢复它（`pi --session`），等它连上桥再送达；start 是开新会话，正文是 `PiLaunch`（开场的话是存储格式，Mac 取原图随第一条消息送达，`piImages`），目录由 Mac 本机解析（项目绑定的代码目录或某会话的目录），在后台开、连上后把开场的话作为第一条消息送进去，经环境变量 `CUEPAD_LAUNCH_TOKEN` 把发起方的认领标识交给扩展，扩展在 hello 里带回，写进同步记录的 `launchToken`，发起方据此打开自己开的那个会话；目录不存在时不启动、按失败写回。托管的进程空闲（没在跑一轮、没在等你确认、子代理也歇下）满 30 分钟退出（记录留着，下次发消息再恢复），App 退出时一并关掉（关它的标准输入，RPC 模式据此正常收尾），界面上结束会话时只关这一个（`PiHost.end(id)`）。用户在别处（自己的终端、herdr）打开了同一个会话时后台进程让出：空闲就马上退，在跑一轮就等这一轮做完再退（不丢已做的工作），退出后让用户那个进程重新载入会话：它这期间没写过就接上那一轮、不分支，写过了（会话已分出支线）就不动并在会话里提示一句；其间同一会话有两个进程连着桥，同步记录跟着用户的那个（不再标托管），后台那个退出也不把记录标为已结束，始终一条；answer 是回答 Pi 正在等的弹窗，正文是 `PiAnswer`，Mac 执行器交给扩展作答、不写发送记录；config 是改会话的模型与思考强度，正文是 `PiConfig` 的 JSON，Mac 执行器交给扩展去改，同 answer 不写发送记录；end 是结束会话，正文固定为 end，不写发送记录、不算发给会话的话（会话的显示状态不把它算进去），Mac 执行器：会话不在本机桥上就按已结束、成功写回，不恢复它；在桥上的，后台托管的关标准输入、开在终端里的走扩展的 end 命令，10 秒内没退出按失败写回；结束的进度只来自发给该会话的结束请求（`DeliveryRequest.shownEnd`，CueStore 里一处，会话页与 Agent 页共用，Agent 页经会话列表的 `ends` 读，界面不另存状态），`requestEnd` 遇到还在路上的结束请求就返回它、不写第二条；ping 是连接测试，Mac 执行器收到即按成功写回、不碰目标与 Pi、不写发送记录，iOS 设置·同步的"测试到 Mac 的连接"连发 10 条，看往返与三段（上传、到 Mac 执行完、回到手机；后两段用 Mac 写回的完成时间，跨设备时钟）的中位数），Mac 界面的发送目标与投送请求都用它，只在调用 Pi 桥时落成桥的 steer/followUp。**发给 Pi 只有投送请求一种记录**：Mac 上发给 Pi 会话（会话页的回复框、灵感与任务的发送按钮、菜单栏稿纸）也是写一条指定本机 `hostID` 的投送请求，由本机执行器与手机发来的请求同一流程执行——送达、写发送记录、带任务时把任务关联到该会话（`recordSend` 同一事务）——发起的界面等结果再提示；直接发送而会话正忙时不写请求，先问马上说还是等它做完再说；发给应用、复制到剪贴板仍直接执行。手机经同步下发的投送请求里读到本版本不认识的值时原样保留、Mac 不执行、按失败写回，不静默当成已知值。失败原因一律读 `DeliveryRequest.failure`：执行器写回只接受成功或带原因的失败，别的版本写来、没带原因的记录读出唯一的兜底"Mac 没有说明原因"，界面不再各写一句。
- **投送**：进程内 `Dispatcher` actor，经前台应用/剪贴板/按键三个协议接缝测试。顺序靠任务链而非 actor 本身（actor 在 await 处可重入）。激活先订阅通知再调用，超时报错不发键；目标未运行时报错且不动剪贴板。单条目同时放文字与 PNG 时，图形应用只取其一，所以含图的灵感写成按原顺序含图的 RTFD 并附纯文字兜底。辅助功能授权归属 CuePad.app。窗口隐藏与发送记录由调用方负责。
- **命令行**：`cuepad` 随 App 分发在 `CuePad.app/Contents/Helpers/cuepad`，由 `CuePadCLI` 目标统一构建、随 App 签名与公证。设置窗口底部的开关在 `~/.local/bin/cuepad` 建符号链接（位置被别的文件占用时不覆盖，App 被移动后能检测并一键修复；不做需要提权的 /usr/local/bin）。它与 App 用同一套资料库位置规则。
- **测试**：Swift Testing 覆盖 Store、同步映射、Pi 会话解析与桥协议、投送队列、命令行；另有"构建 → 运行 → 截图"的视觉验收流程。测试只用替身或不产生按键事件的系统调用，不向其他应用发送键鼠事件；服务测试用临时目录、独立 UserDefaults 与记录型替身，不碰真实资料库、`~/.pi` 和其他应用。全局热键的物理触发与跨应用粘贴只能人工验证。

## 同步

主 App 启动时创建 `CloudSync` 并启动：两个入口（Mac 的 `AppDelegate`、iOS 的 `Launch`）都以 `sync: .iCloud` 构造 `AppServices`，由 `AppServices.makeSync` 按位置与本构建的 iCloud 权限决定（隔离模式 `CUEPAD_LIBRARY_DIR` 与没有 iCloud 权限的本机构建不创建引擎）；该参数没有默认值，测试用 `.custom(替身)`。没有引擎或引擎没能启动时 `syncStatus` 是写明原因的 `.unavailable`，引擎确认账号前是 `.starting`，界面不会显示成"已同步"；未登录 iCloud 或关闭了本 App 的 iCloud 显示 `.noAccount`，文案告诉用户去哪打开（`SyncSummary`）。Mac 启动时注册远程通知，引擎才能收到别的设备改动的静默推送；回到前台、Mac 系统唤醒时立即 `syncNow()`，推送由引擎自己处理。静默推送按低优先级投递，不保证送达与时效；而 CKSyncEngine 只拉它已知"有变化"的 zone（名单只由推送、切到前台与"太久没拉"填上），没有推送时手动 `fetchChanges`（含限定 zone 的写法）不发任何请求。所以手里有正在等的东西时由 `SyncPoller`（CueSync，输入是此刻的拉取节奏，nil 表示不在等）开始在等时立即、之后按节奏调 `CloudSync.pullChanges()`：`ZoneChangePuller` 不经引擎、直接拉同步区的变化（`CKFetchRecordZoneChangesOperation`），交给协调器与引擎同一个 `.fetched` 合并入口（幂等）；令牌只在内存，第一次只带版本与状态（`modifiedAt`、`state`、`status`）把令牌推进到现在（其间看到的"在等的表"——投送请求与 Pi 会话状态——本机已有的只在服务器上较新时补取，本机没有的只补取还没完的（已结束的会话——几千条历史——与已有结果的投送请求由引擎带来），按 ID 每次至多 400 条（CloudKit 单次请求上限）取整条交给协调器，补取完成才记下令牌，不被令牌跨过），过期则重取，持久的权威仍是引擎状态。节奏只在 `AppServices.pollingCadence` 定义：Mac 桥上有 Pi 会话连着（以桥为准）或有本机要执行的投送请求时每 2 秒；手机有还没结果的投送请求时每 2 秒、每次在等最多 2 分钟，正在看 Agent 页或会话近况时每 3 秒，进入后台即停、回前台恢复。手机写出投送请求（发送、作答、连接测试）后、Mac 执行器写回结果后，都立即只上传这一条（`CloudSync.sendNow`），不等引擎的自动调度（Mac 上相邻两次自动上传可相隔二十多秒）。推送仍是主通道。`CloudSync.stateUpdates` 推送"状态 + 问题"快照（状态不变时新增或重复的问题也送达），`AppServices` 据此暴露 `syncStatus`、`syncIssues`，另有 `conflicts` 与 `resolveSync`、`resolveConflict`。待推送的登记由数据库推导：启动、处理同步决定时全量对账；之后每次本机提交只登记这次改动的记录（SQLite update hook 记下的改动行）；别的进程（命令行）写过库、或有登记因配额等失败被搁置时，下一次改动全量对账；`syncNow`（回到前台）先按数据库重新登记再发送。CloudKit 一批记录整体提交：一条被拒，同批其余以 `batchRequestFailed`（22）失败，引擎不替它们重试，所以同步逻辑把它们重新登记；冲突里本机版本胜出时同样重新登记；真正被拒的进问题列表，下次改动时重试。Mac 端把 Pi 会话写成同步记录，一个会话一条（记录 id 由 Pi 的会话 id 算出，重启、恢复不变）：在线会话的状态、待确认的问题、是否后台托管、子代理列表（名字与此刻在干什么，加密字段里的 JSON）与当前模型、思考强度、可选的模型（`model`、`thinking`、`models`，加密字段；`models` 在会话结束时清空）来自 Pi 桥；手机经 `AppServices.configure` 请求改模型与思考强度（投送方式 config）、经 `AppServices.end(_:)` 请求结束会话（投送方式 end），与作答（`answer`）同一通路、写出后立即上传，改模型只对在线会话开放；会话的对话（同步表 `piMessages`，一条消息一条记录、只追加，正文至多 8000 字符）与记录上的摘要（最近一轮做完的问与答、进行中的提问）只来自会话文件，是同一次读文件、同一事务写出的投影（`CueStore.writePiTranscript`），文件一变就写、不经状态记录的节流，Mac 本机界面也读它：最近 7 天活跃过的会话写全部消息，更早的只写摘要，手机打开时发投送方式 `transcript` 请那台 Mac 从会话文件补写；Mac 启动时与之后每天清理一次：会话（按会话文件的最后活动）安静 7 天、对话也是 7 天前写出的就删；已结束的会话没有进行中的提问（读出时定，会话重新连上就又有）；你的消息带着送进它的投送请求 id（`deliveryID`，扩展写进会话文件），界面据此把请求气泡换成这条消息，历史会话来自本机的会话文件索引（写成已结束；在线的不覆盖；内容没变不重写，免得每次启动把几千条历史重新上传）；会话结束（启动时包括本机上次遗留的）标为已结束、近况留着；已结束的记录与会话文件同存亡（回填完成时删掉没有会话文件的）。完整路径不同步，只有文件夹名与项目。界面只读同步记录，经唯一的查询 `CueStore.piSessionPage`（按范围：在线/已结束/全部，按文字、项目、认领标识、记录 id，分页带总数；每项带发给该会话的最近一条说话或作答的投送请求，同一次查询按会话聚合读出）；不整表读。回填完成时还补写有会话文件却没有记录的会话（如升级前建的索引）。项目在哪台 Mac 上绑定了代码目录也同步给手机（`DirectoryBinding`，每个项目与 Mac 一条，只有目录末段名与 Mac 名，完整路径只在本机表）：由 Mac 从本机绑定推导，启动时对一次、绑定变化时跟上；手机据此列出能开新会话的项目并确定发给哪台 Mac。首次上线时几千条历史经引擎按每批至多 250 条上传，在后台进行，不阻塞界面。Mac 并只执行发给本机 `hostID`（硬件 UUID 的哈希前缀）的投送请求（手机发来的与本机自己写的）；执行器读写 Store 失败经 `onIssue` 上报，不吞掉（请求会停在原状态，手机那边一直等）。投送请求的往返时间（`DeliveryRequest.roundTrip`，创建 → 结果回到本机）由发起的设备在应用远端结果时用本机时钟记下，存在同步表的本机列里，不进 CloudKit。

**灵感与任务合并的升级**：本地库升级把旧的任务表逐条插成 `Card`（`todoAt` 有值、层级与状态照搬），id 是 `DeterministicID.uuid("task-card/<旧任务 id>")`（结构版本 14；只由旧 id 算出，各设备不论先后升级都得到同一个；新 id 已存在——别的设备已经升级、同步过来——时同一个任务留较新的一份、引用并入它：整行较新者胜，与同步冲突的规则一致，不做字段级合并），上级、冲突原卡、发送记录与投送请求里的引用跟着改；不沿用旧 id 是因为同一个 recordName 在 CloudKit 里只能对应一种记录类型，服务端拒绝改类型（invalid attempt to update record from type X to Y），一种记录并进另一种时都不能沿用 id；发送记录与投送请求里的 `taskID` 并进 `cardID`，删掉任务表；项目的目标卡不再是特殊记录：介绍 `intro` 取旧目标卡的第一行、去掉"目标："前缀，原卡留作普通灵感。同步记录类型 `tasks`、字段 `projects.goalCardID` 与 `sendRecords.taskID`、`deliveryRequests.taskID` 退役。所有设备须同时升级：没升级的设备上改任务会丢（它写的是已退役的类型），改灵感会丢掉新字段（层级、任务与状态）。迁移里任何会因数据冲突失败的语句都会让启动失败，改迁移时要考虑别的设备已经同步过来的数据。

**Agent 锁屏通知**：Pi 会话状态记录带明文可查询的 `notify` 标志（"等你确认"、"完成"的转换那一次写入上置位）。它是一次性事件标志，只存在于未上传的版本上：服务端接受上传即清（`CueStore.markPushed`），远端带回的 `notify` 一律不收（含自己上传的回声）；带标志的写入由 `PiStateRecorder.update` 返回，Mac 据此立即上传这一条（`AppServices.upload`）。CloudKit 服务端订阅在标志置位时直接生成可见通知，不依赖静默推送与 App 在后台运行；订阅由 iOS 在启动、账号变化和每次回到前台确保（幂等），结果是 `SyncState.alerts`（off / active / failed(原因)），失败不抛、状态带上服务端的原因，每次回到前台重试；点通知路由到对应会话。"要不要提示"只有一条规则 `PiAlert.entering`（进入等你确认；从工作中进入完成；首次看到的会话不提示），Mac 置位标志与手机前台的 App 内横幅（见「iOS / iPadOS」）都用它；App 在前台时系统通知不展示，由横幅负责。服务端发出的只是本地化 key 的通用句（标题与详情是加密字段，服务端看不到）；订阅带"可改写"标记，iOS 的通知服务扩展（`App/NotificationService`，目标 CuePadNotify，`com.sugeh.cuepad.notify`）收到后用记录 id 从同一容器取回记录、在设备上解密，改写成"会话名 在等你 + 问题首行"或"会话名 + 完成了"（`CueSync.PiAlertText`），取不到就保持通用句。通知反映服务端收到记录那一刻的状态：标志在上传前被状态已前进的后续写入取代就不送出，同状态的更新则沿用标志——状态记录不是事件日志，要保证每个事件都送达需要单独的追加式通知事件记录，那是另一种设计。该字段的可查询索引由生成的数据结构声明，已部署到生产环境。

### 排查与真机验证

App 自己的日志都在 subsystem `com.sugeh.cuepad`（类别 `services`、`launch`、`shutdown`、`pi-history`）；CloudKit 与 CKSyncEngine 的日志在 `com.apple.cloudkit`：

```bash
log show --last 30m --info --debug --predicate 'subsystem == "com.sugeh.cuepad" OR (process == "CuePad" AND subsystem BEGINSWITH "com.apple.cloudkit")'
log stream --info --predicate 'process == "CuePad" AND subsystem BEGINSWITH "com.apple.cloudkit"'   # 实时看
```

引擎日志里的错误详情是 `<private>`，看不到原因。要复现：拿用户库的副本、清掉引擎状态，用真实的同步代码在带生产签名的最小程序里跑一遍、读问题列表——它会真的上传副本里的待推送记录，只在确认副本内容就是用户本机那份时做。

同步是否真在跑，以库为准（只读复制出来看，不碰用户的库）：`syncState` 有一行 `engine`（引擎序列化的状态），`syncRecords` 的行数随推送增长到与同步表记录数相当。真机验证：装发布版 → 打开设置的同步分区，应先显示"正在连接 iCloud…"再变"已同步"（未登录或关掉本 App 的 iCloud 时显示去哪打开）→ 几分钟内复制库检查上面两张表 → 另一台设备上能看到同一批项目、灵感与任务。验证生产环境的订阅能否创建：用 Developer ID 描述文件签名、带 production 容器权限的最小 Mac 程序保存订阅，打印完整的 CKError（看 `description`，`localizedDescription` 会丢掉服务端的说明）；开发环境的 Mac 描述文件按 Provisioning UDID 登记设备，不是 Hardware UUID。

### CloudKit 数据结构

数据结构由同步记录映射推出，不手写：`apple/CloudKit/cuepad.ckdb` 是生成物，`CloudKitSchemaTests` 保证它与映射一致；映射改了测试会失败，在 `apple/CuePadKit/` 下用 `CUEPAD_REGENERATE_SCHEMA=1 swift test --filter regenerateSchemaFile` 重新生成，再导入开发环境。管理令牌存在钥匙串 `cuepad-cloudkit-management-token`，不入库、不打印：

```bash
export CLOUDKIT_MANAGEMENT_TOKEN=$(security find-generic-password -a cuepad -s cuepad-cloudkit-management-token -w)
C="--team-id SVPPQJM9JG --container-id iCloud.com.sugeh.cuepad --environment development"
xcrun cktool validate-schema $C --file apple/CloudKit/cuepad.ckdb
xcrun cktool import-schema $C --validate --file apple/CloudKit/cuepad.ckdb
xcrun cktool export-schema $C --output-file /tmp/dev.ckdb   # 回读：服务端把字段按字母序排列并补系统字段，逐类型核对字段与权限
```

开发环境的结构已导入并回读核对，生产环境已部署（含 `piSessionStates` 的 `model`、`thinking`、`models`，回读与开发环境一致）。生产环境的结构只能增不能删，开发环境导入的结构也不能删去生产已有的字段与类型：已下线的记录类型 `tags`、`cardTags`、`probes`、`tasks` 与字段 `cards.isFavorite`、`cards.numbering`、`projects.goalCardID`、`projects.sortKey`、`sendRecords.taskID`、`deliveryRequests.taskID` 在生成器里（`CloudKitSchema.retiredTypes` / `retiredFields`）照原样声明，客户端不再读写；灵感与任务合并在 `cards` 上新增的 `parentID`、`todoAt`、`startedAt`、`completedAt`、`piSessionID` 与 `projects.intro` 已部署到生产环境（回读与开发环境一致）。结构 16 给 `cards` 加了 `archivedAt`（INT64，已导入开发环境并回读，生产环境待部署）。结构 15 给 `sendRecords` 与 `deliveryRequests` 各加了明文 `partIDs`（STRING，带上的灵感 id 的 JSON 数组），已导入开发环境并回读，生产环境待部署（发版前必须先部署）。生产环境只能在 CloudKit 控制台网页点「Deploy Schema Changes」部署开发环境的结构，所以映射再改时需重复"生成 → 导入开发环境 → 控制台部署"。订阅也是 schema 的一部分，但不在 `.ckdb` 里，cktool 看不到也导不出：生产环境拒绝客户端创建没部署过的查询订阅（CKErrorDomain 12，底层 BadSyntax 2006，服务端原文 attempting to create a subscription in a production container），区域订阅与数据库订阅不受此限；订阅类型按通知形状匹配（换成 alertBody 的变体会被拒）。所以改订阅的定义（谓词、选项、通知文案 key）要先让开发环境签名的构建在开发容器里保存同样的订阅，再在控制台 Deploy Schema Changes——确认页的 Record Types、Indexes、Security Roles 都显示 0、也不单独列出订阅，但部署照样生效。

## 平台

### macOS 壳层

主窗口在 `MainWindowFactory` 创建时就设好外框（内容铺到透明标题栏下），界面不要再在运行时改窗口样式；设置窗口（⌘,）由 `SettingsWindowController` 承载；`CuePadApplication` 在退出前结束挂在窗口上的弹窗，⌘Q 与 SIGTERM 才不会被 sheet/alert 卡住；退出时先等服务收尾（停止远程投送执行器、同步引擎、Pi 连接与全局快捷键）再放行，整体最多等约 2 秒，卡住的组件不拦着退出、记一条 `shutdown` 日志指出是哪个；收尾的等待不在主线程上、回复经主 run loop 的 common modes 送达（`terminate` 可能是在主线程上的任务里调用的，那时系统在嵌套事件循环里等回复，主线程上排队的任务轮不到），所以同步引擎等组件的接口不能隶属主线程（`SyncControlling` 是 `nonisolated`）；菜单栏面板 `MenuBarPanel` 随内容尺寸变化，顶边固定在图标下方。单元测试以 App 为宿主，宿主检测到 `XCTestConfigurationFilePath` 时不启动壳层，避免注册真实全局热键和菜单栏图标。

### iOS / iPadOS

- 资料库在 App Group 共享容器 `group.com.sugeh.cuepad` 的 `Library/`（库文件、`Attachments/`、待入库的 `Capture/`、给小组件的 `Snapshots/`），偏好用同名 UserDefaults 套件。模拟器直接可用；真机需要开发者账号给三个目标（App、分享扩展、小组件）签上该 App Group。
- 资料库始终只有主 App 写：分享扩展把内容放进 `Capture/`，主 App 在前台、收到扩展的进程间通知时入库；小组件与扩展不打开资料库，只读主 App 写的 JSON 快照。
- 每个窗口（iPad 多窗口）各有一个 `SceneContext`，选中项目不放进全局偏好。

## 视觉

内容是纸，控件是玻璃：编辑器、灵感与任务用安静的实色底并保留纸感品牌；底子是纸与墨（logo 与吉祥物的两种颜色），文字、图标与系统控件的 tint 是墨；签名色朱砂（`signature`）只落在焦点上，一屏通常一两处：主按钮与发送钮、选中项的浅底（`selection` 加粗体，Mac 侧栏与 iOS 共用，不用系统灰胶囊）、选中的筛选胶囊、进行中的任务与 Agent 工作中（`working`）；其余彩色只表示要你注意的状态（等你确认赭黄、出错胭脂，与朱砂色相拉开，再配形状）与项目；有新回复是墨色实心点（形状区别于待你回复的灰勾）；纸面从上沿极轻地提亮、上沿一线高光（`paper()`），与玻璃同一种光；三层同一色温由深到浅：侧栏 < 桌面 < 纸，深色是"夜里的纸"（暖黑），令牌在 `UI/Shared/Theme/Palette.swift`；位移与尺寸用无回弹弹簧，时长不超过 300ms；按压只有四类（圆钮与胶囊 `PressStyle`、整卡 `CardPressStyle`、行 `RowPressStyle` 只亮底不缩放、主按钮是系统玻璃），按下快、松开带一点回弹，圆钮与卡片按下一下轻触感；计数变化时数字滚动（`counting`）；常驻的循环动效只有 Agent 工作中状态标身后的呼吸，一轮做完放一圈朱砂涟漪；呼吸用 Core Animation（SwiftUI 的 repeatForever 与符号动效每帧在 App 进程里重算，Agent 页静止时也占约 9% CPU）；减弱动态效果时退为短淡入淡出、不呼吸（`Motion`）；空态与出错页一律是吉祥物加一句现状（`EmptyState`，图在 Assets 的 `mascot-*`，由 `design/final/ip-*.png` 经 `design/tools/cutout.swift` 抠出、缩到 360px），不用系统 `ContentUnavailableView`；iOS 的 `-CuePadScene style` 是视觉样板（token、纸与玻璃、各类按压、状态标与动效），改主题时对照；工具栏、侧栏、弹层、菜单栏面板用系统 Liquid Glass 组件，玻璃不叠玻璃；"降低透明度""增强对比度"开启时自动退回实底。中文正文一律苹方。界面不解释内部规则：分组的依据写在代码里，不写成给用户看的说明文案。界面上只说 Agent：Pi 会话一律叫"Agent 会话"，项目页（iPhone 与 Mac）与 Mac 侧栏的会话分组标题是"Agent"；"Pi"只用于 Pi 这个产品本身（安装、升级、连接、扩展、版本、模型与 `pi` 命令），代码里的类型名 `Pi*` 不变。

## 资料库与隔离

位置规则唯一来源是 `CueStore` 的 `LibraryLocation`：macOS 在 `~/Library/Application Support/CuePad/Library/`，iOS 在 App Group 容器；环境变量 `CUEPAD_LIBRARY_DIR`（必须是绝对路径）指向隔离目录，资料库、偏好设置（主题、快捷键、当前项目、窗口位置）都放进去，不导入旧库，不碰真实的 `com.sugeh.cuepad` 偏好域，并行实例互不影响。App、命令行与测试都经它取位置。

资料库打不开（迁移失败、更新版本建的库、损坏）时不终止进程：唯一入口 `AppServices.openLibrary(at:)` 抛出 `LibraryFailure`（原文、路径、结构版本、是更新版本建的还是升级失败），iOS 与 Mac 都显示 `UnreadableLibraryView`：人话说明、折叠的详情、重试、导出诊断（复制原因、路径、结构版本与本版本支持的版本、App 版本）；没有任何写入入口，打不开也不会换成空库；项目目录读取失败的页面（`CatalogGate`）用同一个组件。位置本身有误（没有 App Group 权限、`CUEPAD_LIBRARY_DIR` 不是绝对路径）时，iOS 同样走这一页，Mac 仍提示后退出；Mac 上打开失败弹一个独立的失败窗口，重试成功后自动关闭。

macOS 首次启动从旧版（Electron 时代）数据库 `~/Library/Application Support/CuePad/cuepad.db` 导入一次：只读源库的副本（含 `-wal`），映射为新模型，幂等；完成标记是库目录里的 `.electron-import-completed`。

## 视觉验收

`shot mac` 直接启动产物里的可执行文件并记下它的 PID（不经 LaunchServices 激活，不抢焦点；上次中断遗留的实例只按记下的 PID 结束），按该 PID 找窗口 ID 后 `screencapture -l` 只截该窗口（首次需给终端授予屏幕录制权限）；以 SIGTERM 退出，走应用正常退出流程。`shot ios` / `shot ipad` 构建 → 模拟器安装启动 → 截图 → 终止，库与偏好放进 `.derived/library-ios`。`--` 之后是 App 启动参数：

```bash
apple/scripts/xc.sh shot mac out.png -- -CuePadDemo YES -CuePadScene editor -theme dark
```

- Debug 构建认 `-CuePadDemo YES`（空库时写入演示数据）、`-CuePadProject <名称>`、`-CuePadScene <collapsed|older|editor|search|tasks|trash|settings|menubar|projectform|session>`、`-CuePadSearch`、`-CuePadCard`、`-CuePadWindowSize 1280x800`、`-CuePadBench <sidebar|motion|resize|churn|perf|press>`（press 配 `-CuePadPressAt x,y` 在该点按下、松开打开、拖走取消、再像键盘那样直接打开，每个事件打印主机时间，可与按窗口号录的 ScreenCaptureKit 帧逐帧对齐，第一次按下时同一轮亮出一个原生红块作"最早能变的那一帧"的对照；开合侧栏 10 次 / 记一条灵感后开合纸页，这两项结束自动退出，供 Instruments 或连拍取帧；resize 在侧栏开合途中拉窄窗口，留给截图核对页宽；churn 边加灵感边逐点拉宽窗口；perf 见下面「性能测量」）、`-CuePadSeed perf`（空库时写入性能测量用的大库）、`-CuePadWindowOrigin x,y`（窗口可放到屏幕外）、`-CuePadImport <旧库路径>`（界面起来后导入旧版资料库）、`-CuePadCatalogFailure YES|once`（项目目录读取报错：YES 每次都失败，核对失败画面；once 每个窗口与菜单栏面板只有第一次失败，按"重试"后恢复，核对重试路径）、`-CuePadAXDump YES`（iOS：界面起来 4 秒后把读屏看到的元素按顺序写进资料库目录的 `ax-dump.txt`，没有 UI 测试目标时核对无障碍），说明见 `App/Sources/UI/Debug/DebugScene.swift`；设置项可直接覆盖（`-theme dark`）。`settings`、`menubar` 画面把设置窗口、菜单栏面板的内容放进主窗口拍，因为只截主窗口。
- `CUEPAD_SHOT_LIBRARY` 换库目录（默认 `.derived/library`），`CUEPAD_SHOT_SETTLE` 是出窗后等待渲染的秒数。
- Pi 目录同样隔离（`.derived/pi-agent`、`/tmp/cuepad-shot-<uid>`），截图不含 `~/.pi` 的会话。隔离的 Pi 目录里没装扩展，侧栏底部出现"连接 Pi"征求同意是正确状态；不要它时传 `-piExtensionDeclined YES`（只写入参数域，不改已保存的设置）。
- 布局反馈环压力场景：`apple/scripts/layout-stress.sh [CuePad.app]`（缺省取 `$CUEPAD_DERIVED` 的 Debug 构建）跑三组隔离实例——屏幕外最小窗口下 Pi 会话快速结束/新建并在思考中/出错间跳、1280×907 下 Pi 全状态轮换、常驻滚动条下边加灵感边拉宽，本机有真实 pi 时再加两组真实 Pi 会话「发提示词 → 出错/完成 → 开新会话 → 立刻再发」（`apple/scripts/pi-real-churn.py`，离线假模型 `pi-stress-model.ts`，每轮等上一轮结束再开新会话，会话文件真实落盘，并断言 Pi 会话文件与应用历史确实产生、否则判为没覆盖到）——按进程日志里的 "Geometry action is cycling" 与 "has continued for 300 iterations" 判定，有则退出码 1。检测器自检：`layout-stress.sh --inject-loop` 给每组挂上刻意的几何回写环（`-CuePadGeometryLoop YES`），必须以 1 退出，证明它抓得到这类环。Pi 轮换由 `apple/scripts/pi-churn.py` 假扩展提供。界面约束：工具栏内容只随用户操作与数据变化，不随滚动位置、尺寸等布局读数变化；几何读数（`onGeometryChange` / `onScrollGeometryChange`）不写回影响自身排版的状态，按宽度切换排版用 `Layout` 或 `ViewThatFits` 当场决定；推入页的底色铺在导航容器上（`containerBackground(_:for: .navigation)`，iOS 在推入路由的统一入口 `RouteView` 一处铺），不铺在滚动区上，否则数据没到的几帧整页透明露出系统黑；顶栏的工具栏项在推入时就建好、之后只换其中的内容，控件随数据置灰而不出现消失（推入转场期间系统不重建工具栏项，换项要等转场结束才显示，纸页的标题会晚到近一秒）。
- 性能测量：`apple/scripts/perf-mac.sh [次数]` 构建打开编译优化的 Debug（测量代码只在 Debug 里），第一次在隔离库里写入合成大库（50 项目、5000 条灵感其中 300 条带 4032×3024 大图、200 个 Pi 历史会话、500 条发送记录），之后每次冷启动跑 `-CuePadBench perf`，输出一行 JSON：冷启动到首屏灵感出现、内存（phys_footprint）、项目页滚轮快速上下滚（每帧 40pt）与开合纸页的帧间隔、⌘K 每个关键词的 Store 查询中位数与打开面板到结果读到。帧间隔的口径：主线程上 display link 两次回调之间的时间（`hitchesAt` 列出每次超过刷新间隔 1.5 倍的位置与时长），反映主线程跟不跟得上，不是画面实际交出的帧率——渲染服务一侧的节奏也会推迟回调，画面没在动时的长间隔用户看不到。是否真的掉帧以 Instruments 的 Animation Hitches（`--template 'Animation Hitches' --attach <pid>`，看 hitches 表的时长与"app update / render"归因）为准；定位主线程开销用 Time Profiler，看主线程在等什么用 System Trace 的线程状态。Animation Hitches 在 iOS 模拟器上不支持（报 "Hitches is not supported on this platform"），iOS 端用模拟器录屏逐帧或应用内每帧探针取证。窗口在后台也能测（display link 照常走），不用抢前台。界面约束：点开纸页的那一格点下即按下（`CardOpenStyle`，0.98）——按下由主窗口的本地事件监听在 AppKit 分发鼠标按下时记到这一格上（鼠标停着的那一格，早于 SwiftUI 按钮识别），点下那一帧直接缩到 0.99、余下再缓动（动画第一帧进度为零），松开稍等 80ms 再放开（打开中接上就不弹）；准备期间由它自己保持按下（开合阶段 `opening`），纸在开始放大的那一帧以按下的样子接过它；会动的过渡里，重活（创建编辑器、挂底栏、让编辑器接过键盘）放在动之前、每帧一步（等屏幕下一次刷新再做下一步，主队列异步可能挤回同一帧），动起来之后每帧只剩动画与改透明度；大容器（主窗口）的视图体不读开合这类频繁变化的状态，读它的部分拆成小视图；大量行的区域用懒加载栈（"更早"上千行全建出来时，每个滚轮事件的命中测试与每帧布局都按行数增长）；灵感墙的每一格不读整窗共享、随开合变化的状态，开合状态按格分开（`CardPresence`），位置读数只在它被打开期间挂上。
- 窗口位置/尺寸会被系统记住（`NSWindow Frame main`），截图尺寸以上次为准；恢复默认：`defaults delete com.sugeh.cuepad "NSWindow Frame main"`。

## 签名与发布

本机构建走 ad-hoc 签名（`xc.sh` 覆盖工程默认的团队与身份，并换用不含 iCloud/推送的 macOS 权限文件）；签名事实源是 `App/Config/Signing.xcconfig`。发布与真机构建是手动签名：Xcode 的自动签名用 API 密钥时管不了 App Group 与 iCloud 容器，所以证书与描述文件由 `scripts/provision.py` 经 App Store Connect API 创建，工程里各 target 指定名称（只对 `iphoneos` 与 macOS 的 Release 生效，模拟器与日常构建不受影响）。

凭据文件 `~/.appstoreconnect/cuepad.env`（不入库）的字段：`ASC_KEY_ID`、`ASC_ISSUER_ID`、`ASC_KEY_PATH`（App Store Connect API 密钥 `.p8` 的路径）、`CUEPAD_TEAM_ID`；`xc.sh release ios` 另需 `CUEPAD_TESTER_EMAIL`（加入内部测试组的 App Store Connect 用户邮箱）。Apple Distribution 证书的私钥放专用钥匙串 `~/.appstoreconnect/cuepad-signing.keychain-db`。缺凭据文件时 build/test/shot 照常，只有下面的发布命令会报错；密钥内容不会打印。

| 命令 | 作用 |
| --- | --- |
| `xc.sh provision` | 幂等：创建 App ID 与能力（App Groups、iCloud、推送）、Apple Distribution 证书、iOS 与 macOS 描述文件 |
| `xc.sh release mac` | 刷新描述文件 → 归档（Developer ID）→ 导出 → `notarytool` 公证 → 装订 → `spctl` 与 `codesign` 校验 → `<产物目录>/release/mac/CuePad-<版本>-mac.zip`，并生成 `appcast.xml`（见「自动更新」） |
| `xc.sh release ios` | 刷新证书与描述文件 → 归档 → 导出 IPA → `altool` 上传 → 建/取内部测试组「内部」并加入账号持有人（构建号取时间戳，自动递增） |
| `xc.sh device` | 登记连接的真机 → Development 证书与描述文件 → 开发构建 → 安装并启动 |
| `scripts/testflight.py builds` | 列出 TestFlight 构建与处理状态 |

权限：主 App 有 iCloud（CloudKit，`iCloud.com.sugeh.cuepad`）、推送（`$(APS_ENVIRONMENT)`：Debug development，Release production）与 App Group（iOS）；扩展只有 App Group；macOS 另有 Apple Events 自动化（终端跳转）。辅助功能权限使 Mac 版不能进 Mac App Store，走官网分发并用 Sparkle 更新。

只能在网页上做的一次性前置：App Group `group.com.sugeh.cuepad` 与 iCloud 容器 `iCloud.com.sugeh.cuepad` 的创建及挂到 App ID（主 App 与通知服务扩展 `com.sugeh.cuepad.notify` 都要挂）；Developer ID Application 证书（账号持有人创建，CSR 由 `provision.py devid-csr` 生成，`provision.py devid-import <.cer>` 导入）；App Store Connect 里的 App 记录。

## 自动更新（macOS）

用 Sparkle 2（EdDSA 校验、增量更新），以官方二进制 xcframework 引入：`Vendor/Sparkle/Package.swift` 只有一个 `binaryTarget`（url + checksum，升级版本改这一处），不拉 Sparkle 源码。更新源 `https://cue-pad.com/appcast.xml` 与公钥在 `App/Config/CuePad-macOS-Info.plist`；设置窗口底部有"自动检查更新"开关和"检查更新…"，App 菜单里也有"检查更新…"。隔离模式（`CUEPAD_LIBRARY_DIR`）不启动更新器。

EdDSA 私钥在专用钥匙串（`~/.appstoreconnect/cuepad-signing.keychain-db` 里的 `cuepad-sparkle-ed25519`，不入库；`scripts/sparkle.sh key` 首次运行时生成并打印公钥）。`xc.sh release mac` 用时间戳作构建号（Sparkle 按 `CFBundleVersion` 比较新旧，每次发布必须递增），在公证、装订后把 zip 收进更新历史目录 `~/.appstoreconnect/cuepad-updates/` 并生成 `appcast.xml`（含与历史版本的增量包，所以历史 zip 必须留在这里；它在产物目录之外，清理产物目录或换 `CUEPAD_DERIVED` 不影响），`appcast.xml` 另复制到 `<产物目录>/release/mac/`。更新包的下载地址前缀用 `CUEPAD_UPDATE_URL_PREFIX`（默认 `https://cue-pad.com/downloads/`）；更新历史目录里的 zip、增量包与 `appcast.xml` 部署到对应位置由人决定。
